# تطوير وتحسين المشروع — منصة الصدارة

> ملف حيّ نُكمله لاحقاً. يجمع: (1) ميزات مخطّطة، (2) مشاكل مُكتشَفة بأسبابها الجذرية وحلولها المقترحة — **قبل التنفيذ**.
> آخر تحديث: 2026-10-06.

الحالة الحالية للإصدار المنشور: **v2.4.5** (سجل العقارات: عقار/QR/مواطن/خدمات/مهام + بيانات المواقع المشتركة مع الساز).

---

## 0) متابعة: ربط أجر الصيانة التراكمي بفوترة الساز (خطوة تالية)

في v2.4.6 أصبح أجر الصيانة قابلاً للتعريف على **المنطقة + العنوان 2 + العنوان 3**، والأجر الإجمالي = **المجموع التراكمي** (منفّذ ومعروض في سجل العقارات عبر `GET /api/properties/maintenance-fee`).
**المتبقّي:** تطبيق المجموع على **فوترة مشترك الساز**. حالياً مشترك الساز يرتبط بالمنطقة فقط (`SasSubscriberProfile.RegionId`) ويُطبَّق أجر المنطقة (أو يُدخَل يدوياً في تبويب التجديد: حقل «أجور صيانة (اختياري)» في [sas_renewal_tab.dart](../src/Apps/CompanyDesktop/alsadara-ftth/lib/sas_agent/pages/sas_renewal_tab.dart)).
**الخطة:** إضافة `Address2Id`/`Address3Id` إلى `SasSubscriberProfile` + منتقي هرمي في واجهة مشترك الساز + ملء حقل الصيانة تلقائياً = `computeMaintenanceFee(region,addr2,addr3)`. **يمسّ وحدة الساز وفوترتها ⇒ عبر وكلاء `sas-*` + موافقة (منطق دفع).** الحالة: **مُصمَّمة، غير منفّذة.**

## 1) المرحلة E — ربط FTTH ببيانات المواقع المشتركة (مؤجّلة — للتنفيذ لاحقاً)

### السياق
في v2.4.5 أصبح لدينا **مصدر موحّد للمناطق** (`SasRegion`) + بنية هرمية (المنطقة → العنوان 2 → العنوان 3)، يستهلكها:
- **الساز**: مشترك الساز يرتبط بالمنطقة عبر `SasSubscriberProfile.RegionId` (موجود وعامل).
- **سجل العقارات**: العقار يرتبط عبر `Property.RegionId/Address2Id/Address3Id`.

**الهدف من المرحلة E:** جعل **FTTH** يرتبط بنفس المناطق، لتوحيد التقارير والتوجيه الجغرافي عبر الأنظمة الثلاثة (ساز + FTTH + عقارات).

### التصميم المقترح
| خطوة | المحتوى |
|------|---------|
| **E1 — البيانات** | إضافة `RegionId` (Guid?, FK→SasRegion, SetNull) إلى كيان **`ServiceRequest`** (طلبات/مهام FTTH)، واختيارياً `Address2Id/Address3Id`. migration إضافية (آمنة، nullable). يمكن أيضاً إضافة `RegionId` إلى `Citizen` إن أردنا ربط المواطن جغرافياً مباشرةً. |
| **E2 — الواجهة** | في نماذج FTTH (إنشاء طلب خدمة / بيانات المواطن) نضيف **منسدلات المنطقة/العنوان** من نفس النقطة `GET /api/properties/regions` + `/address2` + `/address3` (أو نقطة مرآة تحت `/api/service-requests/regions`). نفس مكوّن المنسدلات المستخدم في نموذج العقار. |
| **E3 — التقارير** | تقارير موحّدة بالمنطقة: عدد مشتركي الساز + طلبات FTTH + العقارات لكل منطقة. (لوحة جغرافية مشتركة.) |

### نقاط انتباه
- العزل: المناطق معزولة بالشركة أصلاً — أي ربط FTTH يخضع لنفس `CompanyId`.
- الصلاحية: قراءة المناطق في FTTH يمكن أن تُفتح بصلاحية FTTH الحالية (لا نفرض `property_registry` على شاشات FTTH) — نضيف نقطة قراءة مناطق بصلاحية مناسبة أو نسمح للقراءة بأي مستخدم ضمن الشركة.
- لا كسر: `ServiceRequest` حالياً فيه `City/Area` نصّيان — نُبقيهما كلقطة ونضيف `RegionId` بالتوازي (dual-write مثل نمط Department/TechnicianName).

### الحالة: **مُصمَّمة، غير منفّذة.** تبدأ عند طلب المالك.

## 2) مشكلة: فشل إضافة موظف جديد

### الوصف
عند إضافة موظف جديد قد يفشل الحفظ. معالجة الخطأ في الواجهة ضعيفة (تُظهر «خطأ» عاماً عند الاستثناء) فيصعب تمييز السبب.

### مسار الإضافة (مُتحقَّق)
- **الواجهة:** [users_page_vps.dart](../src/Apps/CompanyDesktop/alsadara-ftth/lib/pages/users_page_vps.dart) — حوار `_AddEditEmployeeDialog`، دالة `_save()` ترسل:
  `POST /internal/companies/{companyId}/employees` (عبر `useInternalKey: true`).
  الحقول الإلزامية: الاسم + الهاتف (كلمة المرور افتراضية `123456`).
- **الباكند:** [InternalDataController.cs](../src/Backend/API/Sadara.API/Controllers/InternalDataController.cs) — `CreateCompanyEmployee()`. سلسلة التحقّق: API Key → وجود الشركة → حدّ `MaxUsers` → **تفرّد الهاتف** → **تفرّد البريد** → توليد كود أمان → حفظ.

### السبب الجذري (سببان متتاليان — مُتحقَّقان)
1. **فحص تفرّد الهاتف/البريد عام لا لكل شركة:** في `CreateCompanyEmployee` يُفحَص `PhoneNumber`/`Email` على **كل المستخدمين** بلا شرط `CompanyId`. فإن كان الرقم مستخدماً في **شركة أخرى** يُرفَض بـ«رقم الهاتف مستخدم بالفعل».
2. **فهرس قاعدة بيانات فريد عام (الأخطر):** على جدول `Users` في الإنتاج يوجد `IX_Users_PhoneNumber` = **UNIQUE عام** (مُتحقَّق بـ`pg_indexes`). فحتى لو صُحِّح فحص الـController، سيفشل الإدراج بـ500 (انتهاك قيد فريد) عند تكرار الرقم عبر الشركات. (البريد: فهرس **غير فريد** `IX_Users_Email` ⇒ تفرّد البريد مفروض فقط في الكود، لا في القاعدة.)

> ملاحظة: نفس نمط v2.3.6 الذي حوّل تفرّد هاتف **الوكلاء** إلى «لكل شركة». الموظفون (Users) ما زالوا على التفرّد العام.

### الحل المقترح (مرحلتان)
- **الكود:** في `CreateCompanyEmployee` (وأي مسار تحديث مماثل) أضِف `&& u.CompanyId == id` لفحصَي الهاتف والبريد.
- **القاعدة (migration + تطبيق مباشر):** استبدال الفهرس العام بفهرس مركّب فريد:
  ```sql
  DROP INDEX IF EXISTS "IX_Users_PhoneNumber";
  CREATE UNIQUE INDEX "IX_Users_PhoneNumber_Company"
    ON "Users" ("CompanyId", "PhoneNumber") WHERE "IsDeleted" = false;
  ```
  وتحديث `SadaraDbContext` (السطر ~544) إلى `HasIndex(e => new { e.CompanyId, e.PhoneNumber }).IsUnique()`.
  **تحذير:** قبل الحذف، تأكّد من عدم وجود هواتف مكرّرة حالياً عبر الشركات (فحص استباقي)، وإلا سيفشل إنشاء الفهرس المركّب. خطة rollback: إعادة الفهرس العام.
- **الواجهة:** تحسين `_save()` لإظهار رسالة الخادم الحقيقية عند الاستثناء (بدل «خطأ») + تسجيل.

### موافقات لازمة
تغيير فهرس قاعدة إنتاج ⇒ يمرّ على **database-postgres-agent** + خطة rollback + نسخة احتياطية (القاعدة المالية). تغيير يمسّ العزل ⇒ **security-auditor-agent**.

### الحالة: **مُشخَّصة، غير منفّذة.**

## 3) مشكلة: إعدادات واتساب لا تُحفظ محلياً (تُضبط من جديد كل مرة)

### الوصف
في كل فتح للتطبيق/الشاشة يحتاج المستخدم لإعادة ضبط إعدادات واتساب — كأنها لا تُحفظ أو لا تُحمّل.

### التشخيص (مُتحقَّق) — **ثلاثة أنظمة إعدادات منفصلة بمفاتيح مختلفة**
1. **وحدة الساز:** [wa_settings.dart](../src/Apps/CompanyDesktop/alsadara-ftth/lib/sas_agent/whatsapp/config/wa_settings.dart) — `WaSettingsStore`، مفاتيح `wa_mode` + `wa_server_url`، افتراضي `http://127.0.0.1:3100`. يُحمَّل في `initState` لشاشة [wa_settings_screen.dart](../src/Apps/CompanyDesktop/alsadara-ftth/lib/sas_agent/whatsapp/ui/wa_settings_screen.dart).
2. **خدمة النواة:** [whatsapp_server_service.dart](../src/Apps/CompanyDesktop/alsadara-ftth/lib/whatsapp/services/whatsapp_server_service.dart) — مفاتيح `whatsapp_server_url` + `whatsapp_server_enabled` + تأخير الدفعات، تخزين Firebase + SharedPreferences (cache) **لكل شركة tenantId**، افتراضي `http://145.223.82.114:3000`.
3. **إعدادات النظام:** [whatsapp_system_settings_service.dart](../src/Apps/CompanyDesktop/alsadara-ftth/lib/whatsapp/services/whatsapp_system_settings_service.dart) — مفاتيح `whatsapp_renewal_system` + `whatsapp_bulk_system`، SharedPreferences فقط.

### السبب الجذري (الفرضيات الأرجح — تحتاج تأكيداً عند التنفيذ)
- **تضارب المفاتيح:** النظام الأول يحفظ في `wa_server_url`، بينما أنظمة النواة تقرأ `whatsapp_server_url` ⇒ ما يُحفَظ من شاشة الساز لا تجده شاشات النواة (والعكس).
- **لا تحميل مركزي عند الإقلاع:** لا مكان واحد يحمّل الإعدادات بعد تهيئة الجلسة؛ شاشات مختلفة تحمّل مفاتيح مختلفة، وبعضها (مثل تحميل في `subscription_details_page`) لا يحمّل `wa_mode`/`wa_server_url` أصلاً.
- **نطاق تخزين مختلط:** النظام الأول **عام** (SharedPreferences)، والثاني **لكل شركة** (Firebase/tenantId) ⇒ عند تبديل الشركة/الجلسة قد تختفي القيم الظاهرة.
- **حفظ غير منتظَر:** بعض `onChanged` تستدعي `_persist()` بلا `await` ⇒ قد تُغلق الشاشة قبل اكتمال الحفظ.
- **احتمال مسح عند الخروج:** يجب التأكد هل تسجيل الخروج/تبديل الشركة يمسح مفاتيح `whatsapp_*` ([main.dart](../src/Apps/CompanyDesktop/alsadara-ftth/lib/main.dart) يمسح tokens فقط — لا يمسح إعدادات واتساب، لكن يجب فحص مسارات logout الأخرى).

### الحل المقترح (مرحلتان)
- **فوري:** توحيد مفاتيح التخزين (مفتاح واحد لكل إعداد عبر كل الأنظمة) + توحيد الخادم الافتراضي + إضافة `await` لكل حفظ + تحميل مركزي للإعدادات عند الإقلاع بعد الجلسة.
- **هيكلي:** دمج أنظمة الإعدادات الثلاثة في خدمة واحدة (`WhatsAppSettingsService` موحّدة)، tenant-aware (لكل شركة)، مع مصدر حقيقة واحد (Firebase أو الخادم) و cache محلي متزامن. إزالة `WaSettingsStore` المنفصل واستخدام الخدمة الموحّدة في شاشة الساز.

### نقطة انتباه
إعدادات واتساب لكل شركة = الحل الصحيح طويل الأمد (مذكورة سابقاً كـ«إصلاح B» في مذكرة تجديد واتساب). توحيد المفاتيح أولاً يمنع التضارب الحالي.

### الحالة: **مُشخَّصة، غير منفّذة.** (الفرضيات تحتاج تأكيداً نهائياً بالتتبّع الحيّ عند بدء التنفيذ.)

## خلاصة الأولويات (عند استئناف العمل)
1. **مشكلة إضافة الموظف** — أثرها تشغيلي مباشر (يمنع إضافة موظفين). تتطلب تغيير فهرس إنتاج بموافقة.
2. **إعدادات واتساب** — إزعاج متكرر؛ الحل الفوري (توحيد المفاتيح) سريع ومنخفض الخطورة.
3. **المرحلة E (ربط FTTH)** — توسعة ميزة؛ تبدأ عند طلب المالك.
