# المرحلة 4 — مقترح مخطط الدُّفعات/الصلاحية + الوحدات (بانتظار موافقة)

> **حالة:** مقترح تصميم فقط. **لا كود ولا migration نُفِّذ.** يتطلّب موافقة بشرية صريحة
> (قاعدة ذهبية: أي تغيير مخطط = migration جديدة تمرّ على database-postgres-agent +
> security-auditor-agent). لا يُطبَّق على الإنتاج بلا إذنك.
> محدَّث: 2026-10-31 · الفرع: `fix/inventory-tenant-isolation-p2`.

## لماذا مؤجَّل عن بقية المرحلة 4
اللوحة/التنبيهات والتصدير أُنجزت فوراً لأنها تُبنى من الكيانات القائمة بلا تغيير مخطط.
أمّا الدُّفعات والصلاحية والوحدات المتعددة فتحتاج جداول/أعمدة جديدة ⇒ migration ⇒ موافقتك أولاً.

## ما هو موجود اليوم (الأساس)
- وحدة واحدة لكل مادة: `InventoryItem.Unit` من enum `InventoryUnitType`
  (Piece/Meter/Roll/Box/Kilogram/Liter/Set…). **لا تحويل بين الوحدات.**
- المخزون كمية صحيحة لكل (مستودع+مادة): `WarehouseStock.CurrentQuantity` **int**،
  بمتوسط كلفة مرجّح `AverageCost`. **لا تتبّع دُفعات ولا تواريخ صلاحية.**

## المقترح (أ) — الدُّفعات وتواريخ الصلاحية

### كيان جديد `StockBatch` (ITenantScoped)
| حقل | نوع | ملاحظة |
|-----|-----|--------|
| Id | long | PK |
| CompanyId | Guid | عزل + فهرس |
| WarehouseId | Guid | FK |
| InventoryItemId | Guid | FK |
| BatchNumber | string? | رقم الدُّفعة/التشغيلة |
| Quantity | int | المتبقّي من الدُّفعة |
| UnitCost | decimal | كلفة هذه الدُّفعة تحديداً |
| ReceivedAt | DateTime | تاريخ الاستلام |
| ExpiryDate | DateTime? | الصلاحية (nullable لمواد بلا صلاحية) |

- فهرس فريد مقترح: `(CompanyId, WarehouseId, InventoryItemId, BatchNumber)`.
- فهرس للصلاحية: `(CompanyId, ExpiryDate)` لتنبيهات «قارب على الانتهاء».

### الأثر على المنطق
- **الاستلام** (CreatePurchaseOrder/Receive/ConfirmInvoice-شراء): بدل تحديث `AverageCost`
  فقط، يُنشئ `StockBatch` جديدة؛ `WarehouseStock.CurrentQuantity` يبقى كمجموع مشتق (أو
  يُحسب من الدُّفعات). `AverageCost` يبقى للتوافق الخلفي والتقارير.
- **الصرف/البيع**: خصم **FEFO** (الأقرب انتهاءً أولاً) أو FIFO — قرار سياسة.
  `CostAtSale` يصبح كلفة الدُّفعة المخصومة فعلاً (أدقّ من المتوسط). ⚠️ **تغيير محاسبي** —
  يحتاج موافقة accounting-agent.
- **تنبيهات جديدة**: يُضاف إلى `GET /api/inventory/alerts` قسم `expiringSoon`
  (صلاحية خلال N يوماً) و`expired`.

### هجرة ومخاطر
- migration إضافية فقط (جدول جديد) — لا تعديل أعمدة قائمة ⇒ منخفضة الخطر على الموجود.
- خيار التدرّج: إبقاء `AverageCost`/`CurrentQuantity` كما هما (مصدر الحقيقة الحالي)
  وإضافة الدُّفعات كطبقة موازية اختيارية لكل مادة (علَم `TrackBatches` على المادة)،
  فلا تتعطّل المواد التي لا تحتاج دُفعات.

## المقترح (ب) — الوحدات المتعددة والتحويل

### خيار B1 (أخفّ): لا مخطط جديد
- جعل `InventoryUnitType` قائمة عرض فقط وإبقاء وحدة واحدة لكل مادة (الوضع الحالي).
- لا حاجة migration. **لا يحلّ** حالة «الشراء بالصندوق والبيع بالقطعة».

### خيار B2 (كامل): كيان `ItemUnit`
| حقل | نوع | ملاحظة |
|-----|-----|--------|
| Id | long | PK |
| CompanyId | Guid | عزل |
| InventoryItemId | Guid | FK |
| Name | string | مثل «صندوق» |
| ConversionToBase | decimal | كم وحدة أساس في هذه الوحدة (صندوق=12) |
| IsBaseUnit | bool | وحدة الأساس |

- كل الكميات تُخزَّن بوحدة الأساس؛ الواجهة تعرض/تُدخِل بأي وحدة وتضرب/تقسم على
  `ConversionToBase`. يتطلّب تعديل DTOs الشراء/البيع لحمل `UnitId`.
- أثقل: يمسّ معظم مسارات الكمية ⇒ يحتاج تغطية اختبارات موسّعة قبل أي نشر.

## التوصية الهندسية (للنقاش)
1. ابدأ بـ **(أ) الدُّفعات/الصلاحية** بنمط «طبقة موازية اختيارية» (علَم `TrackBatches`)
   — أعلى قيمة تشغيلية (تنبيهات انتهاء)، أقلّ خطر، migration إضافية فقط.
2. أجّل **(ب) الوحدات** إلى **B2** في دفعة منفصلة لاحقة بعد تغطية اختبارات كاملة،
   لأنه يمسّ منطق الكميات في كل مكان.
3. أي قرار على `CostAtSale` من كلفة الدُّفعة = **تغيير محاسبي** يمرّ على accounting-agent
   + security-auditor-agent قبل التنفيذ.

## ما ينتظر قرارك
- [ ] الموافقة على كيان `StockBatch` + سياسة الخصم (FEFO أم FIFO).
- [ ] هل `CostAtSale` يتحوّل لكلفة الدُّفعة، أم يبقى المتوسط المرجّح؟ (أثر محاسبي)
- [ ] الوحدات: B1 (لا تغيير) أم B2 (تحويل كامل)؟
- [ ] إذن بإنشاء الـmigration محلياً على الفرع (بلا تطبيق إنتاج).
