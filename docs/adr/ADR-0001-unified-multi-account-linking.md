# ADR-0001: الحسابات الخارجية المرتبطة المتعددة لكل موظف (واجهة موحّدة فوق الموجود)

- **الحالة (Status)**: مقبول (Accepted) — قرار المالك. التنفيذ لم يبدأ بعد؛ المواضع الحسّاسة تحتاج موافقة بشرية صريحة قبل التنفيذ (انظر «المواضع التي تحتاج موافقة»).
- **التاريخ**: 2026-10-17
- **المقرِّر**: المالك (قرار معتمد) — صياغة ومراجعة معمارية: architecture-evolution-agent
- **الفرع المرتبط**: `feature/multi-account-linking`
- **الوكلاء المعنيون بالتنفيذ**: backend-agent، database-postgres-agent، security-auditor-agent، mobile-agent (الواجهة)، testing-qa-agent — بتنسيق project-manager.
- **نطاق هذا الـ ADR**: توثيق معماري فقط. لا يعدّل هذا المستند أي كود تطبيق أو مخطط قاعدة بيانات.

---

## 1. السياق (Context)

اليوم يرتبط الموظف الداخلي (كيان `User` في `Sadara.Domain`) بحساب FTTH خارجي **واحد فقط** عبر حقلين مباشرين على الكيان:

- `User.FtthUsername` (`string?`) — «اسم المستخدم في نظام FTTH (null = فني فقط، ليس مشغل FTTH)».
- `User.FtthPasswordEncrypted` (`string?`) — «كلمة مرور FTTH مشفرة (AES) — null إذا ليس مشغل FTTH».

هذا التصميم أحادي الحساب (one-to-one مطموس داخل `User`) لم يعد كافياً: الموظف الواحد قد يحتاج ربط **عدّة حسابات FTTH وعدّة حسابات ساس** واختيار أيّها يدخل إليه.

في المقابل، تطوّرت وحدة الساس بالفعل إلى نموذج **متعدّد الحسابات** ناضج عبر الكيان `SasAccount` (في `src/Backend/Core/Sadara.Domain/Entities/SasAccount.cs`):

- `SasAccount : BaseEntity<Guid>, ITenantScoped` — يحمل `CompanyId` (عزل المستأجر) + `OwnerUserId` (دفاع بالعمق فوق فلتر المستأجر) + `Label` + `ServerUrl` + `Username` + `PasswordEncrypted` + `IsActive` + حقول مزامنة.
- كلمة المرور تُشفَّر عبر `ISecretProtector`/`SecretProtector` (ASP.NET Core Data Protection) ولا تُعاد **أبداً** في أي استجابة؛ تُفكّ في الذاكرة فقط عند التمرير الداخلي (مثال: `_secretProtector.Unprotect(account.PasswordEncrypted)` في `SasAgentController` قبل نداء خدمة الساس).
- العزل مفروض صراحةً على مستوى الاستعلام: `CompanyId == tenant.CompanyId && OwnerUserId == currentUserId && !IsDeleted`.
- التهيئة في `SadaraDbContext`: فلتر `!IsDeleted`، فهرس مركّب `(CompanyId, OwnerUserId)`، FK الشركة `Cascade` وFK المالك `Restrict` (لتفادي مسارات حذف متسلسلة متعددة).

> ملاحظة ملكية مهمّة: `SasAccount` والبوّابة `/api/sas-agent/*` هما **من ملكية النواة** (backend-agent + database-postgres-agent)، وليسا جزءاً من وحدة الساس المعزولة في `modules/sas-agent/**`. أي أن توسيع نموذج الحسابات المرتبطة هو شأن معماري للنواة ولا يخترق حدّ ملكية الوحدة، ما دمنا لا نلمس `modules/sas-agent/**` ولا `lib/sas_agent/**` ولا تعريف كيان `SasAccount` نفسه.

**الهدف**: ربط الموظف بعلاقة one-to-many مع حسابات FTTH وحسابات ساس، مع واجهة/طبقة دخول موحّدة تجمع النوعين، دون المساس بما استقرّ في الساس ودون كسر التوافق القائم.

## 2. القرار (Decision)

اعتماد **«واجهة موحّدة فوق الموجود» (Unified Facade over Existing)**:

1. **كيان جديد `FtthAccount`** في `Sadara.Domain/Entities` يُبنى **على غرار `SasAccount` بدقّة** (نفس نمط الأمان والعزل)، يمثّل حساب FTTH خارجياً واحداً مربوطاً بموظف:
   - يرث `BaseEntity<Guid>` ويوسم `ITenantScoped`.
   - الحقول المقترحة: `CompanyId` (عزل المستأجر)، `OwnerUserId` (دفاع بالعمق)، `Label` (تسمية وصفية يختارها الموظف)، `Username`، `PasswordEncrypted` (مشفّرة عبر `ISecretProtector`، لا تُعاد أبداً)، `IsActive`، وحقول اختيارية مثل `ServerUrl`/`LastSyncAt`/`SyncStatus` إن لزم للتوافق مع تدفّق الدخول الحالي (`dual_auth_service`/مزوّد FTTH).
   - تهيئة `SadaraDbContext` مطابِقة لنمط `SasAccount`: فلتر `!IsDeleted`، فهرس مركّب `(CompanyId, OwnerUserId)`، FK الشركة `Cascade` وFK المالك `Restrict`.

2. **طبقة تجميع/دخول موحّدة** عبر `LinkedAccountsController` جديد (مسار مقترح مثل `/api/linked-accounts/*`):
   - يُرجِع قائمة موحّدة تجمع صفوف `FtthAccount` + صفوف `SasAccount` للموظف الحالي، مع تمييز `kind` (ftth | sas) وبيانات العرض الآمنة فقط (بلا أي كلمة مرور).
   - يفرض العزل الثلاثي نفسه على كل عنصر: `CompanyId == tenant.CompanyId && OwnerUserId == currentUserId && !IsDeleted`.
   - **القراءة من `SasAccount` قراءةً فقط** للتجميع والعرض؛ **لا يُعدَّل تعريف كيان `SasAccount` ولا مخططه ولا منطق وحدة الساس**. أي تعديل على `SasAccount` خارج نطاق هذا الـ ADR ويخضع لمالكه.

3. **الدخول خادمي (server-side)**: الموظف يختار أي حساب (ftth أو sas) يدخل إليه؛ الباكند:
   - يفكّ تشفير كلمة المرور في الذاكرة فقط (`ISecretProtector.Unprotect`)،
   - يسجّل الحدث (audit)،
   - ينفّذ الدخول لدى المزوّد الخارجي المناسب،
   - يعيد **توكناً/نتيجة جلسة فقط** — لا يُعاد السرّ إلى العميل إطلاقاً.
   - الدخول لحساب ساس يبقى يمرّ عبر البوّابة القائمة `/api/sas-agent/*` → خدمة Python (لا يُعاد تنفيذه في الطبقة الموحّدة)؛ الطبقة الموحّدة توجّه لا أكثر.
   - **مستقبلاً** (خارج هذا الـ ADR): وضع «الدخول للاثنين معاً ودمج البيانات».

4. **زرّ إظهار كلمة المرور** عبر endpoint **مصرّح ومُسجَّل (audit)** حصراً، لا ضمن أي قائمة؛ بنفس أسلوب الساس (فكّ في الذاكرة + تسجيل + صلاحية صريحة).

5. **التوافق (backward compatibility)**:
   - هجرات **إضافية فقط** (جدول `FtthAccounts` جديد) — بلا حذف/تعديل لأي migration قائمة.
   - حقلا `User.FtthUsername`/`User.FtthPasswordEncrypted` **يبقيان مؤقتاً** (قراءة/كتابة كما هي)، وتُضاف مرحلة ترحيل (backfill) لاحقة تنسخ القيمة المفردة القائمة إلى صفّ `FtthAccount` افتراضي لكل موظف له قيمة.
   - endpoints الدخول/الربط القديمة **تبقى عاملة** حتى تنتقل الواجهة بالكامل، ثم تُنظَّف في مرحلة لاحقة بقرار منفصل.

## 3. البدائل المرفوضة (Rejected Alternatives)

### البديل أ — جدول حسابات خارجية موحّد واحد يبتلع الساس (`ExternalAccount` مع عمود `Provider`)

الفكرة: جدول واحد `ExternalAccount(Provider = Ftth | Sas, ...)` يوحّد النوعين في كيان ومخطط واحد، وتُرحَّل صفوف `SasAccount` الحالية إليه ويُحذف/يُهجَر `SasAccount`.

| المعيار | التقييم |
|--------|---------|
| نقاء النموذج | جذّاب نظرياً (جدول واحد، استعلام واحد) |
| المساس بالساس | **يخرق حدّ القرار الصريح**: يتطلب لمس كيان `SasAccount` وترحيل بياناته وربما منطق `SasAgentController`/التسعير/المزامنة/وحدة الساز المرتبطة به |
| المخاطر | عالية: `SasAccount` مرتبط بـ `SasPackagePrice`/`SasSubscriberProfile`/`SasCitizenPayment`/مناطق عبر `SasAccountId` (FKs مركّبة فريدة). توحيده يكسر هذه العلاقات أو يفرض ترحيلاً واسعاً وخطيراً على مخطط إنتاج حيّ |
| التوافق | يتطلب هجرة ترحيل بيانات (data migration) على جدول قائم بالإنتاج — عكس مبدأ «هجرات إضافية فقط» |
| التراجع (rollback) | معقّد: استرجاع بيانات مُرحَّلة ومحذوفة صعب وخطِر |

**سبب الرفض**: يبتلع نموذجاً ناضجاً ومستقراً (الساس) بلا عائد يوازي كلفته، ويخرق قرار المالك الصريح («لا نلمس كيان `SasAccount`»)، ويُدخل مخاطر ترحيل عالية على مخطط إنتاج حيّ مع علاقات FK متشعّبة. الفائدة (استعلام واحد) تتحقّق أصلاً عبر طبقة التجميع في `LinkedAccountsController` دون أي من هذه المخاطر.

### البديل ب — توسيع `User` بمجموعات حقول متعددة (FtthUsername2، FtthUsername3، ...)

توسيع أفقي للحقول المفردة على `User`. **مرفوض**: مضادّ لنمط العلاقات (anti-pattern)، لا يتوسّع (كم حساباً؟)، يضخّم كيان `User`، ولا يوفّر عزل `OwnerUserId`/فهرسة لائقة.

### البديل ج — إبقاء الحقول المفردة وربط FTTH متعدّد عبر جدول وصل فقط دون محاذاة نمط الساس

ربط FTTH بجدول جديد لكن بنمط أمان/عزل مختلف عن `SasAccount`. **مرفوض**: يُنتج نمطين أمنيين متباينين للسرّ نفسه (كلمة مرور خارجية)، ويصعّب المراجعة الأمنية والصيانة. محاذاة نمط `SasAccount` بدقّة تعطي تماثلاً معمارياً وتقلّل سطح الخطأ.

## 4. النتائج والمخاطر (Consequences & Risks)

### إيجابيات
- **تماثل معماري**: FTTH والساس يتبعان نفس نمط الكيان (`ITenantScoped` + `OwnerUserId` + `PasswordEncrypted` عبر `ISecretProtector`)، ما يبسّط المراجعة والصيانة والاختبار.
- **عزل سليم**: كل حساب معزول بثلاثية شركة + مالك + حذف منطقي، مطابِق لما استقرّ في الساس.
- **تغيير منخفض المخاطر**: إضافي بالكامل (جدول + كونترولر + هجرة إضافية)، بلا مساس بالساس ولا بالمخطط القائم.
- **توافق محفوظ**: الحقول/endpoints القديمة تبقى حتى الانتقال الكامل.

### مخاطر وتخفيفها

| الخطر | المستوى | التخفيف |
|------|---------|---------|
| عزل المستأجرين: تسريب حساب موظف لموظف/شركة أخرى | عالٍ (P0 منطقياً) | فرض `CompanyId == tenant.CompanyId && OwnerUserId == currentUserId && !IsDeleted` على **كل** استعلام (قائمة/دخول/إظهار). ختم `CompanyId`+`OwnerUserId` عند الكتابة من **التوكن** لا من العميل (كما في `SasAgentController`). الختم يبقى مستقلاً عن علَم `Tenancy:EnforceIsolation` (تفادي انحدار صفوف `NULL` السابق). مراجعة security-auditor-agent إلزامية. |
| تسريب السرّ (كلمة المرور) | عالٍ (P0) | التخزين مشفّر عبر `ISecretProtector` فقط؛ لا يُعاد في أي قائمة/رد؛ الإظهار عبر endpoint مصرّح + audit؛ الفكّ في الذاكرة فقط عند الدخول الخادمي. فقدان مفاتيح DataProtection (`.dpkeys/`) يكسر الفكّ — لا تُلمس. |
| تعدّد الحسابات: غموض «الحساب الافتراضي»/الاختيار | متوسط | `Label` وصفي + `IsActive`؛ الواجهة تُلزم الموظف باختيار صريح قبل الدخول؛ لا دخول ضمني. |
| التراجع (rollback) | متوسط | لأن التغيير إضافي: التراجع = إيقاف الواجهة الجديدة والعودة لـ endpoints القديمة؛ جدول `FtthAccounts` يبقى خاملاً بلا أثر على المسار القديم (الحقول على `User` لم تُمَسّ). الهجرة الإضافية لها `Down` واضح. |
| الترحيل (backfill) للصفوف القديمة | متوسط | مرحلة منفصلة ولاحقة؛ نسخ غير مدمّر (الحقول القديمة تبقى)؛ تُختبر محلياً أولاً. |
| ازدواج مصدر الحقيقة (الحقول القديمة + الجدول الجديد) خلال الفترة الانتقالية | متوسط | توثيق واضح أن الجدول هو المصدر الجديد بعد الـ backfill؛ خطة تنظيف محدّدة زمنياً في المرحلة 5؛ تجنّب الكتابة المزدوجة إن أمكن. |
| القراءة من `SasAccount` في الطبقة الموحّدة تتحوّل لتعديل | منخفض/متوسط | حدّ صارم: قراءة فقط؛ لا تعديل تعريف/مخطط `SasAccount`؛ أي تعديل يخرج عن الـ ADR ويمرّ على مالكه + architecture-evolution. |

### استثناء معتمد: كشف كلمة مرور الساس/FTTH لأدمن الشركة (قرار مالك)

وافق المالك صراحةً على كشف كلمة مرور الساس (وأيضاً FTTH) في تبويب الموظف ضمن ميزة «الحسابات المرتبطة»؛ وهذا يستثني — بشروط — الثابت القديم «الاعتماد مشفّر ولا يُعاد في أي استجابة». ضوابط الاستثناء الإلزامية:

- **أدمن الشركة فقط**: الكشف مقصور على أدمن الشركة عبر endpoint مخصّص في بوّابة الحسابات المرتبطة، لا ضمن أي قائمة/رد عام.
- **علَم إعداد `Sas:AllowCredentialReveal`**: **OFF افتراضياً**؛ لا كشف إطلاقاً ما لم يُفعَّل صراحةً.
- **تدقيق مُعمَّر في قاعدة البيانات**: كل عملية كشف تُسجَّل (audit) بشكل دائم.
- **rate-limit**: تحديد معدّل على نقطة الكشف لتقليل سطح إساءة الاستخدام.
- هذا قرار مالك موقّع، ومُراجَع/معتمد من security-auditor-agent. يبقى التخزين مشفّراً عبر `ISecretProtector`، والفكّ في الذاكرة فقط، ومفاتيح `.dpkeys/` لا تُلمس.

## 5. خطة المراحل (Phased Plan)

> كل مرحلة تمرّ عبر project-manager؛ المراحل الحسّاسة تحتاج موافقة بشرية + مراجعة الحرّاس المذكورين.

1. **المرحلة 0 — توثيق وموافقة (هذا الـ ADR)**: اعتماد القرار، تحديث `DECISIONS.md`/`ARCHITECTURE.md`. لا كود.
2. **المرحلة 1 — نموذج البيانات (database + backend)**: إضافة كيان `FtthAccount` + تهيئة `SadaraDbContext` (نمط `SasAccount`) + **هجرة EF إضافية جديدة** لجدول `FtthAccounts`. *يحتاج موافقة بشرية (migration) + مراجعة database-postgres-agent + security-auditor (العزل/السرّ).*
3. **المرحلة 2 — طبقة التطبيق + البوّابة (backend)**: خدمة/DTOs للربط والقائمة الموحّدة؛ `LinkedAccountsController` (CRUD لـ FtthAccount + تجميع read-only مع SasAccount + endpoint إظهار مُدقَّق). تطبيق `[RequirePermission(...)]` وصيغة الاستجابة القياسية `{ success, data, ... }`. *مراجعة security-auditor + code-reviewer.*
4. **المرحلة 3 — الدخول الموحّد الخادمي (backend + security)**: مسار اختيار الحساب والدخول الخادمي (توكن فقط) + audit؛ توجيه دخول الساس عبر البوّابة القائمة. *مراجعة security-auditor (يمسّ تدفّق المصادقة) — موافقة بشرية.*
5. **المرحلة 4 — الواجهة (mobile-agent)**: شاشة الحسابات المرتبطة الموحّدة في `alsadara-ftth` (خارج `lib/sas_agent/**`)، اختيار الحساب، زرّ الإظهار. عربي RTL + ثيم sd.
6. **المرحلة 5 — الترحيل والتنظيف (لاحقاً، منفصلة)**: backfill من `User.Ftth*` إلى `FtthAccount`؛ ثم إهمال/إزالة endpoints والحقول القديمة بقرار ADR منفصل. *موافقة بشرية.*
7. **عبر كل المراحل — الاختبار (testing-qa-agent)**: اختبارات تكامل للعزل (شركة/مالك)، عدم تسريب السرّ، سلامة الدخول.

## 6. المواضع التي تحتاج موافقة بشرية + security-auditor

وفق القواعد الذهبية في `CLAUDE.md` (changing authentication/authorization/tenant isolation، database migration):

- **إنشاء جدول `FtthAccounts` + الهجرة الإضافية** → موافقة بشرية (database migration) + database-postgres-agent.
- **تخزين/فكّ سرّ كلمة مرور FTTH + endpoint الإظهار المُدقَّق** → security-auditor-agent (أسرار + audit).
- **مسار الدخول الموحّد الخادمي** → security-auditor-agent + موافقة بشرية (يمسّ تدفّق المصادقة).
- **صلاحيات الطبقة الموحّدة** (مفاتيح `RequirePermission` الجديدة) → تُثبَّت صراحةً (لا وراثة) ومراجعة security-auditor (authorization model).
- **فرض العزل الثلاثي وختم `CompanyId`/`OwnerUserId` من التوكن** → مراجعة security-auditor إلزامية قبل الدمج (tenant isolation = الخطر الأول).

الكلمة النهائية في أي تعارض أمني (أسرار/مصادقة/عزل) لـ security-auditor-agent؛ وفي مسائل المخطط/الهجرة لـ database-postgres-agent؛ وفي الحدّ المعماري لـ architecture-evolution-agent — كلّها تُنسَّق عبر project-manager.

## 7. حدود الملكية المؤكَّدة

- **لا لمس** لـ `modules/sas-agent/**` ولا `src/Apps/CompanyDesktop/alsadara-ftth/lib/sas_agent/**` (ملكية وكلاء `sas-*`).
- **لا تعديل** لتعريف كيان `SasAccount` ولا مخططه ولا منطق وحدة الساز؛ القراءة منه للتجميع فقط.
- العمل كلّه ضمن ملكية النواة: `Sadara.Domain`/`Sadara.Application`/`Sadara.Infrastructure`/`Sadara.API` + واجهة `alsadara-ftth` خارج `lib/sas_agent/**`.
