# ADR-0003: بوّابة FTTH — توجيه كل مرور المزوّد عبر خادم الصدارة

- **الحالة:** مقترح (قيد النقاش — لم يُنفَّذ بعد)
- **التاريخ:** 2026-10-21
- **السياق المرتبط:** حجب IP خادمنا من مزوّد FTTH، و«قاعدة العزل الذهبية» (الواجهة تنادي الصدارة فقط)

---

## 1. المشكلة والهدف

**المشكلة الحالية:** تطبيق الصدارة ينادي مزوّد FTTH (`admin.ftth.iq` / `api.ftth.iq` / `dashboard.ftth.iq`) **مباشرة من جهاز كل موظف** في **57 موضعاً** بالكود. فالمزوّد يرى مرور FTTH من **عشرات العناوين المتفرّقة** (أماكن/أجهزة مختلفة)، ولا سيطرة لنا على:
- حجب/whitelist العناوين (كل جهاز عنوان مختلف).
- حجم الطلبات ومعدّلها.
- تخزين التوكن (كل جهاز يصادق مستقلاً).
- توحيد ترويسات WAF والتدقيق.

كما يُخالف هذا «قاعدة العزل الذهبية» للمشروع.

**الهدف:** **IP واحد** (خادم الصدارة `72.61.183.61`) هو المصدر الوحيد لكل مرور FTTH ⇒ سيطرة كاملة + whitelist دائم لعنوان واحد + تخزين توكن + حدّ معدّل + تدقيق موحّد، **بصرف النظر عن موقع/جهاز الموظف**.

```
الآن:   جهاز الموظف ──مباشرة──> admin.ftth.iq        (IPs كثيرة، بلا سيطرة)
الهدف:  جهاز الموظف ──> بوّابة الصدارة ──> admin.ftth.iq   (IP واحد، سيطرة كاملة)
```

---

## 2. التصميم المقترح: بوّابة عكسية شفّافة (Transparent Reverse Proxy)

بدل إعادة كتابة 57 نقطة بنقاط مكتوبة يدوياً (مكلف)، نضيف **بوّابة شفّافة واحدة** في الباكند تُمرّر أي طلب FTTH كما هو.

### 2.1 نقطة البوّابة في الباكند
- مسار catch-all: `(.../){method} /api/ftth-gw/{**path}` يستقبل أي مسار FTTH.
- خطوات المعالجة لكل طلب:
  1. **مصادقة مستخدم الصدارة** (JWT) + تحديد شركته ومالك حساب FTTH (عزل).
  2. **حلّ توكن FTTH** للمستخدم: من الكاش إن صالحاً، وإلّا مصادقة المزوّد مرّة واحدة عبر حسابه المرتبط (منطق `LoginFtth` الحالي) وتخزين التوكن.
  3. **تمرير الطلب** (الأسلوب + المسار + الكويري + الجسم) إلى المضيف الهدف مع توكن FTTH + ترويسات WAF.
  4. **إرجاع رد المزوّد** كما هو للتطبيق (status + body + content-type).
  5. **ضوابط:** allowlist للمضيف/المسار، حدّ معدّل، تدقيق، عزل المستأجر.

### 2.2 تخزين توكن FTTH (Token Caching) — جوهر تقليل الحجب
- يُخزَّن توكن المزوّد لكل حساب مرتبط (مفتاح = AccountId) مع `expires_at` (من `exp` في JWT).
- عند الطلب: إن كان التوكن صالحاً (قبل انتهائه ببرزخ أمان ~60ث) يُعاد استخدامه؛ وإلّا يُجدَّد (refresh_token إن توفّر، أو إعادة مصادقة).
- الأثر: نضرب خادم المزوّد **مرّة لكل عمر توكن لكل حساب** بدل كل طلب ⇒ انخفاض هائل في الطلبات ⇒ احتمال حجب شبه معدوم.
- التخزين: `IMemoryCache` (موجود) للمرحلة الأولى (يُفقد عند إعادة التشغيل = إعادة مصادقة واحدة)، أو أعمدة في `FtthAccounts` لاحقاً للثبات.

### 2.3 الأمان
- **SSRF:** allowlist صارم للمضيفات (`admin.ftth.iq`, `api.ftth.iq`, `dashboard.ftth.iq` فقط) — موجود جزئياً (`IsAllowedFtthServerUrl`). يُمنع أي مضيف آخر.
- **العزل:** المستخدم يصل بيانات حساب FTTH الخاص به فقط (أو أدمن للشركة) — عبر `GetAccessibleAccountAsync` الحالي.
- **السرّ:** كلمة مرور FTTH تبقى مشفّرة ولا تُعاد؛ التوكن فقط يُمرَّر.
- **حدّ المعدّل:** per-user + global (بنية `AddRateLimiter` موجودة).
- **التدقيق:** تسجيل من استدعى ماذا ومتى (بلا سرّ) — نمط AUDIT الموجود.
- **ترويسات WAF:** توحيدها في البوّابة (كما في `FtthLoginAsync` الحالي).

### 2.4 معالجة أعطال المزوّد
- مهلة قصيرة (مثلاً 15ث) + رسالة واضحة: «نظام FTTH غير متاح مؤقتاً من المزوّد» عند timeout/5xx — لا «كلمة مرور خاطئة».

## 3. تغييرات الواجهة (Flutter)

### 3.1 توحيد عنوان FTTH (Phase 0)
- حالياً 57 موضعاً يبني URLs بمضيف صريح (`https://admin.ftth.iq/...`).
- نُركّزها في **عميل/إعداد واحد** (`ftth_api_config.dart` / `FtthApi`) يبني العنوان من **متغيّر أساس واحد** (`FtthGatewayBaseUrl`).
- بعدها تبديل المضيف = **تغيير سطر واحد**.

### 3.2 التوجيه للبوّابة
- `FtthGatewayBaseUrl = https://api.ramzalsadara.tech/api/ftth-gw` بدل `https://admin.ftth.iq`.
- المسارات تبقى كما هي (`/api/subscriptions`, `/api/customers`, ...) فتُمرَّر شفّافاً.
- إزالة إرسال توكن FTTH من العميل (البوّابة تُرفقه) — أو قبوله انتقالياً.

## 4. المراحل (Phased Rollout) مع علَم تبديل

| المرحلة | المحتوى | قابلية التراجع |
|---------|---------|----------------|
| **0** | توحيد بناء عناوين FTTH في إعداد واحد بالواجهة (بلا تغيير سلوك) | كامل |
| **1** | بناء بوّابة الباكند `/api/ftth-gw/**` + allowlist + تمرير التوكن + تدقيق | علَم `Ftth:UseGateway` |
| **2** | تخزين التوكن + حدّ المعدّل + ترويسات WAF موحّدة | — |
| **3** | توجيه الواجهة للبوّابة لأهمّ النقاط أولاً (الدخول/التجديد/المشتركون/العملاء) تحت علَم | تبديل العلَم للرجوع للمباشر |
| **4** | ترحيل بقية النقاط (اللوحة/الزونات/التقارير/التشخيص) | — |
| **5** | منع الاتصال المباشر نهائياً (فحص CI يرفض `ftth.iq` مباشرة في الواجهة) | — |

**علَم التبديل** (`Ftth:UseGateway` أو per-endpoint) يسمح بالرجوع الفوري للمسار المباشر عند أي مشكلة أثناء الترحيل.

## 5. خطة الفحص قبل النشر

1. **اختبارات باكند** (xUnit/Integration):
   - allowlist المضيف (يرفض غير المسموح — SSRF).
   - العزل (مستخدم لا يصل حساب غيره).
   - تخزين التوكن (إعادة استخدام قبل الانتهاء، تجديد بعده).
   - حدّ المعدّل (429 عند التجاوز).
   - تمرير شفّاف صحيح (method/path/query/body/status).
2. **فحص محلي/staging** مقابل المزوّد — **بأقل عدد طلبات ممكن** (احتراماً لقاعدة «لا scan/load-test للمزوّد»): طلب واحد لكل نوع للتأكّد من التمرير والتوكن.
3. **فحص دخان للواجهة**: كل شاشة FTTH مُرحَّلة تعمل عبر البوّابة (مشتركون/تجديد/عملاء/لوحة).
4. **تأكيد النتيجة المعمارية**: المزوّد يرى الطلبات من **IP خادمنا فقط** (فحص سجلّ الخروج/الشبكة).
5. بوّابة التحقّق المعتادة (build/analyze/تدقيق/مراجعة ثانية) قبل أي نشر.

---

## 6. المخاطر والتخفيف

| الخطر | التخفيف |
|-------|---------|
| SSRF عبر البوّابة | allowlist صارم للمضيف + رفض ما عداه |
| تمرير ترويسات حسّاسة خطأً | قائمة ترويسات صريحة (whitelist) لا تمرير أعمى |
| تحميل خادمنا (كل مرور FTTH يمرّ به) | تخزين التوكن + حدّ معدّل + مهلات؛ الحجم الحالي معتدل (≤~2000 شركة) |
| كسر شاشة أثناء الترحيل | علَم تبديل per-endpoint + رجوع فوري للمباشر |
| تغيّر عقد المزوّد | البوّابة شفّافة (لا تفترض بنية) فتتبع أي مسار |
| حجب خادمنا رغم ذلك | whitelist IP من المزوّد (خارج الكود) — يبقى مطلوباً |

---

## 7. خطة التراجع

- كل مرحلة خلف **علَم إعداد** (`Ftth:UseGateway`) — إيقافه يُعيد الواجهة للاتصال المباشر فوراً بلا نشر.
- الباكند إضافي (نقطة جديدة) لا يمسّ المسارات القائمة حتى توجّه الواجهة إليه.

---

## 8. تقدير الجهد والمعالم

- **Phase 0 (توحيد عناوين الواجهة):** صغير–متوسط (تجميع 57 موضعاً تحت إعداد واحد).
- **Phase 1–2 (بوّابة + تخزين + أمن):** متوسط (نقطة proxy واحدة + كاش + allowlist + تدقيق).
- **Phase 3–4 (ترحيل الواجهة):** متوسط (تدريجي بالعلَم).
- **Phase 5 (منع المباشر):** صغير (فحص CI).

**مكسب فوري ممكن قبل اكتمال الجذري:** تخزين التوكن في `LoginFtth` الحالي + whitelist IP = يقلّل الحجب كثيراً بأقل جهد (الخيار «ب» السابق).

---

## 9. نقاط للنقاش (قرارات مطلوبة قبل التنفيذ)

1. **النطاق والوتيرة:** هل نبدأ بالمكسب الفوري (تخزين توكن + whitelist) ثم الجذري تدريجياً، أم مباشرةً البوّابة الكاملة؟
2. **تصميم البوّابة:** شفّافة catch-all (موصى — أقل جهد، تتبع أي مسار) أم نقاط مكتوبة لكل عملية (تحكّم أدقّ، جهد أكبر)؟
3. **تخزين التوكن:** ذاكرة مؤقتة (أبسط) أم أعمدة في `FtthAccounts` (ثبات عبر إعادة التشغيل)؟
4. **الأمن:** هل نكتفي بـallowlist المضيف، أم نضيف allowlist للمسارات أيضاً؟
5. **staging:** هل يوجد بيئة staging مصرّح بها للفحص، أم نفحص محلياً بأقل طلبات للمزوّد؟
6. **whitelist المزوّد:** من يتواصل مع `ftth.iq` لإضافة `72.61.183.61`؟ (يبقى مطلوباً بالتوازي.)
7. **إصدار الواجهة:** الترحيل يحتاج إصدارات Flutter جديدة — نجدولها كيف؟
