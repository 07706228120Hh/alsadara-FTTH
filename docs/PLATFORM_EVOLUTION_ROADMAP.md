# خارطة تطوير منصّة الصدارة — أفضل · أوسع · قابلة للتوسّع والصيانة · مترابطة

> خطة استراتيجية لرفع المنصّة (الصدارة + FTTH + الساس + الواتساب + الأتمتة) إلى مستوى إنتاجي متين قابل للنمو، وربط الخوادم والخدمات الست على هوستنكر بشكل آمن وموحّد.
> مبنيّة على الوضع الفعلي (أكتوبر 2026).

---

## 0) الوضع الحالي — تقييم صريح

**نقاط القوة:** معمارية نظيفة (.NET Clean Architecture) · فصل الطبقات · محاسبة مزدوجة موحّدة · وحدات معزولة (الساس/العقارات/الواتساب) · Flutter متعدّد المنصّات · بنية هوستنكر جاهزة (٦ VPS).

**الثغرات المكتشَفة (أولويات الإصلاح):**
| الثغرة | الأثر | الخطورة |
|---|---|---|
| **لا جدار حماية على أي VPS** (`firewall_group_id=null` للستة) | الخوادم مكشوفة للإنترنت | 🔴 حرجة |
| أسرار/مفاتيح مثبّتة في الكود (مكشوفة بالمستودع) | اختراق محتمل | 🔴 حرجة |
| لا شبكة خاصّة بين الخوادم (تخاطب عبر الإنترنت العام) | أمن + زمن استجابة | 🟠 |
| لا CI/CD (بناء/اختبار/نشر يدوي) | أخطاء بشرية + بطء | 🟠 |
| هجرات يدوية (`migrations.sql`) بلا أتمتة | خطر انحراف المخطّط | 🟠 |
| SQLite لخدمة الساس (ملف مفرد) | لا يتوسّع أفقياً | 🟠 |
| عزل المستأجرين معطّل (`EnforceIsolation=false`) | خطر تسرّب بين الشركات عند النمو | 🟠 |
| لا مراقبة/تنبيهات/تتبّع أخطاء مركزي | عمى تشغيلي | 🟠 |
| منطق محاسبة مكرّر ×3 · عناوين/أسرار مثبّتة | دَين تقني | 🟡 |
| بناء Flutter ويندوز يتعطّل (cppwinrt) · لا نسخ احتياطي مؤتمت | إنتاجية + كارثية | 🟡 |

## 1) المحور الأول — الربط والبنية التحتية (الأهم)

**الهدف:** الخوادم الست تعمل كنظام واحد آمن وموحّد.

1. **بوّابة API مركزية (Reverse Proxy)**: Nginx/Traefik على `s-main.my` — مدخل واحد (HTTPS/TLS تلقائي عبر Let's Encrypt)، توجيه لكل خدمة، rate-limiting، حجب المنافذ الداخلية.
2. **شبكة خاصّة بين الـVPS**: فعّل Hostinger Private Network (أو WireGuard) — الخدمات تتخاطب بعناوين داخلية (الباكند ↔ القاعدة ↔ الساس ↔ الواتساب ↔ n8n) **لا عبر الإنترنت العام**. يُغلق كشف القاعدة/الساس/الواتساب للخارج.
3. **جدران حماية** (🔴 فوري): أنشئ `firewall_group` لكل VPS — افتح فقط 443 (البوّابة) و22 (SSH مقيّد بـIP)، أغلق الباقي.
4. **الحاويات (Docker)**: كل خدمة في حاوية + `docker-compose` لكل VPS (الباكند، الساس sidecar، الواتساب، n8n، Postgres، Redis). نشر متّسق قابل للتكرار.
5. **إدارة الأسرار مركزياً**: ملفات `.env` لكل خدمة (خارج المستودع) أو Vault خفيف؛ **تدوير كل المفاتيح المكشوفة** (راجع `PRE_DEPLOY_CHECKLIST.md`).

### مخطّط توزيع الخوادم المقترح
| الخادم | الدور |
|---|---|
| `s-main.my` (KVM4) | بوّابة API + الباكند .NET + **PostgreSQL** (+ PgBouncer) |
| `alsadara.app` (KVM2) | خدمة الساس sidecar + ملفات التطبيق/التحديثات |
| `WHATS.API` (KVM2) | خادم الواتساب (مفصول — موارده مستقلّة) |
| `srv991906` (KVM4) | n8n (الأتمتة) + **Redis** (طابور أحداث/كاش) |
| `srv1587653` (KVM4) | **المراقبة** (Grafana/Prometheus/Loki) + النسخ الاحتياطي |
| `s2.my` (KVM1) | **staging** (بيئة تجريبية قبل الإنتاج) |

## 2) المحور الثاني — قابلية التوسّع

1. **PostgreSQL**: PgBouncer (تجميع الاتصالات) · فهارس على الجداول الكبيرة (`SubscriptionLogs`/`JournalEntries`/`local_subscribers`) · **تقسيم (partitioning)** للجداول الزمنية الضخمة · نسخة قراءة (read replica) للتقارير مستقبلاً.
2. **SQLite خدمة الساس → PostgreSQL**: ترحيل تخزين الـsidecar إلى Postgres (مخطّط منفصل/قاعدة) — يزيل عنق الزجاجة ويسمح بتعدّد نسخ الخدمة.
3. **Redis**: كاش لملخّصات اللوحات/الساس/التقارير · جلسات · طابور خفيف.
4. **مهام خلفية**: Hangfire/Quartz (.NET) للمزامنة الدورية والتقارير والتنبيهات (بدل الاعتماد على الواجهة).
5. **تفعيل عزل المستأجرين** (`EnforceIsolation`): بعد backfill لـ`CompanyId` الفارغة + ضبط `DefaultCompanyId` — أساس التوسّع لمئات الشركات.
6. **تصميم بلا حالة (stateless)** للباكند → يسمح بموازنة حِمل أفقية لاحقاً.

## 3) المحور الثالث — الجودة والصيانة

1. **CI/CD (GitHub Actions)**: على كل push → `dotnet build/test` + `pytest` (خدمة الساس + اختبارات العقد) + `flutter analyze` → نشر تلقائي لـstaging ثم الإنتاج بموافقة.
2. **المراقبة والرصد**: Serilog → **Grafana Loki/Seq** (سجلّات مركزية) · **Prometheus/Grafana** (مقاييس) · **Sentry** (تتبّع الأخطاء) · فحوص صحّة + تنبيهات (Uptime).
3. **أتمتة الهجرات**: `MigrateAsync` عند النشر مع نسخة احتياطية تلقائية قبلها + خطة تراجع (بدل `migrations.sql` اليدوي).
4. **سداد الدَّين التقني**: توحيد منطق المحاسبة الثلاثي في `SubscriptionAccountingService` الواحد · إزالة بقية الأسرار/العناوين المثبّتة (رفعها لـ`AppSecrets`/env) · توحيد أنماط الاستدعاء.
5. **رفع التغطية الاختبارية**: إصلاح الاختبارات المعطّلة سابقاً (TenantIsolation عبر Testcontainers، فلاتر التاريخ) + اختبارات E2E للمسارات الحرجة.
6. **التوثيق**: تحديث `ARCHITECTURE.md` + Swagger/OpenAPI منشور + أدلة تشغيل (runbooks) للنشر والطوارئ.
7. **بناء Flutter**: تثبيت/استبدال `permission_handler` المسبّب لتعطّل cppwinrt + بناء ويندوز في CI.

## 4) المحور الرابع — الأمان (موازٍ لكل ما سبق)

- 🔴 **جدران حماية + شبكة خاصّة + إغلاق المنافذ الداخلية** (المحور 1).
- 🔴 **تدوير كل الأسرار المكشوفة** + نقلها لـenv/Vault + تفعيل `RequirePermission` fail-closed عامّاً.
- **نسخ احتياطي مؤتمت** (Postgres يومي + أسبوعي، خارج الخادم/offsite) + اختبار الاستعادة دورياً.
- **TLS في كل مكان** (داخلي وخارجي) + تحديثات أمنية دورية للـOS + حصر SSH بمفاتيح وIP.
- تدقيق أمني دوري (security-auditor) + فحص الاعتمادات (مثل ثغرة AutoMapper NU1903).

## 5) المحور الخامس — التوسّع الوظيفي (نموّ المنتج)

- **تطبيقات الهاتف** (Android/iOS): كود Flutter جاهز للتوجيه لمنصّات الهاتف.
- **بوّابة المشترك/المواطن النهائي**: رصيد/فواتير/تجديد ذاتي (الباكند جاهز جزئياً).
- **التكاملات**: بوّابات دفع إلكتروني · SMS · أنظمة ISP إضافية (بعد SAS/FTTH) عبر طبقة تجريد موحّدة.
- **ذكاء الأعمال (BI)**: لوحات تحليلية (أرباح/ذمم/نمو) + تقارير مجدولة.
- **وحدة إشعارات موحّدة** (واتساب + SMS + بريد + تطبيق).

---

## 6) المحور السادس — التكامل الحدثي بين الخدمات

**من التسلسل المتزامن (HTTP متسلسل) إلى الأحداث:**
- **طابور رسائل** (RabbitMQ أو Redis Streams على srv991906): عملية التفعيل تُطلق حدثاً → يستهلكه (المحاسبة · الواتساب · المزامنة · الطباعة) بالتوازي وبمرونة (إعادة محاولة، لا فقدان).
- **n8n** للأتمتة عالية المستوى (تذكيرات/تقارير/تكاملات خارجية) — موجود، يُوسَّع.
- **SSO موحّد**: مصادقة مركزية عبر كل الخدمات (الباكند/الواتساب/n8n) بدل مفاتيح متفرّقة.
- **عقود واضحة** بين الخدمات (مثل تحصين عقد الساس بـ`extra=forbid`) — تُعمّم.

## 7) خارطة المراحل (بالأولوية)

| المرحلة | المحتوى | المدّة التقديرية |
|---|---|---|
| **P0 — تأمين فوري** | جدران الحماية + تدوير الأسرار + نسخ احتياطي مؤتمت | أيام |
| **P1 — ربط وتوحيد** | بوّابة API + شبكة خاصّة + حاويات + env مركزي + staging | 1–2 أسبوع |
| **P2 — جودة** | CI/CD + مراقبة/سجلّات/تنبيهات + أتمتة الهجرات | 1–2 أسبوع |
