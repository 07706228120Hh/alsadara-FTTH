# خطة دمج تطبيق الوكلاء داخل منصة الصدارة كوحدة «صفحة وكيل SAS»

> الهدف: زر «صفحة وكيل SAS» داخل الشركة في تطبيق الصدارة الرئيسي (`alsadara-ftth`) يفتح كل تبويبات تطبيق الوكلاء (لوحة · مشتركون · نظام الساس · تجديد · بلنك · تذاكر)، مع تسجيل دخول موظفين مربوط بحساب الساس ودخول صامت، وعزل ثلاثي (شركة/مستخدم/نظام) بلا أي تسريب.
>
> الاستراتيجية المعتمدة: **الخيار (أ)** — إبقاء منطق الساس Python كخدمة داخلية (sidecar) خلف الصدارة (.NET)، وبناء وحدة Flutter أصلية على نمط FTTH الموجود.

---

## 0) المعمارية المستهدفة للاتصال والعزل

```
Flutter (alsadara-ftth / وحدة lib/sas_agent)
    │  JWT (company_id + role + الصلاحيات تُفحص من DB)
    ▼
Sadara .NET API  (/api/sas-agent/*)   ← يفرض: التوكن + عزل الشركة + صلاحية sas_agent
    │  localhost فقط + X-Internal-Secret + اعتماد المستخدم مفكوك التشفير
    ▼
خدمة الساس Python (sas-service)  127.0.0.1:8100  ← غير مكشوفة للإنترنت إطلاقاً
    │  AES-256-CBC متوافق مع OpenSSL (منطق تطبيق الوكلاء المجرَّب)
    ▼
خادم SAS4 الخاص بمزوّد الوكيل (خارجي)
```

**قاعدة العزل الذهبية:** الواجهة تنادي **الصدارة فقط**. الصدارة وحدها تفكّ تشفير اعتماد الساس وتنادي خدمة Python المحصورة على localhost. لا تصل الواجهة ولا الإنترنت لخدمة Python مباشرة → استحالة التسريب أو انتحال حساب ساس شركة أخرى.

| مبدأ | التطبيق |
|---|---|
| مدخل واحد | الواجهة ↔ الصدارة (.NET) فقط بتوكن موحّد |
| العزل يُفرض في .NET | فلتر المستأجر + صلاحية `sas_agent` + مطابقة `CompanyId`+`OwnerUserId` |
| خدمة Python معزولة | مربوطة 127.0.0.1، سرّ داخلي، بلا مسار Nginx عام |
| الأسرار | مشفّرة (Data Protection) ولا تُعاد في أي استجابة |

## 1) المرحلة 1 — الباكند (.NET): نموذج البيانات والعزل

### الكيانات الجديدة

| الكيان | الوصف | العزل |
|---|---|---|
| `SasAccount : BaseEntity<Guid>, ITenantScoped` | حساب ساس مربوط بموظف (يدعم عدّة حسابات) | `CompanyId` (مستأجر) + `OwnerUserId` |
| `CompanySasSettings : ITenantScoped` (اختياري، 1‑1 مع الشركة) | عنوان خادم ساس افتراضي للشركة يرثه الموظفون | `CompanyId` |

**حقول `SasAccount`:** `Id`, `CompanyId`, `OwnerUserId`, `Label`, `ServerUrl`, `Username`, `PasswordEncrypted` (لا يُعاد أبداً), `AccountType` (enum: `SasManager` = صفحة وكيل · `SasUser` = نظام ساس), `IsActive`, `LastSyncAt`, `SyncStatus`, + حقول التدقيق و`IsDeleted`.

### المهام

| # | المهمة | الملف |
|---|---|---|
| 1.1 | إنشاء `SasAccount` و`CompanySasSettings` بوسم `ITenantScoped` | `Core/Sadara.Domain/Entities/` |
| 1.2 | إضافة `DbSet` + تسجيل فلتر الاستعلام (`!IsDeleted` + المستأجر) | `Infrastructure/Data/SadaraDbContext.cs` |
| 1.3 | إنشاء هجرة EF Core جديدة | `Infrastructure/Data/Migrations/` |
| 1.4 | خدمة تشفير `ISecretProtector` (ASP.NET Data Protection) + تطبيقها على كلمة مرور الساس | `Infrastructure/Services/` + `Program.cs` |
| 1.5 | تسجيل صلاحية `sas_agent` في البذور (Second System) | `Infrastructure/Data/SeedData.cs` |

> ⚠️ **إلزامي لمنع التسريب:** أي كيان ساس **يجب** أن يوسم `ITenantScoped` وأن يُسجَّل له فلتر المستأجر؛ ونسيان ذلك يفتح تسرّباً بين الشركات.

## 2) المرحلة 2 — الباكند (.NET): بوّابة الساس (Proxy Controller)

### نقاط النهاية `/api/sas-agent` — كلها محميّة بـ `[RequirePermission("sas_agent", ..., Second)]`

| المسار | الوظيفة | الفحص الإضافي |
|---|---|---|
| `GET /accounts` | حسابات ساس للمستخدم الحالي (بلا كلمات مرور) | مستأجر + `OwnerUserId == المستخدم` |
| `POST /accounts` | ربط حساب ساس (يشفّر كلمة المرور) | ختم `CompanyId`+`OwnerUserId` |
| `PUT/DELETE /accounts/{id}` | تعديل/حذف حساب | مطابقة المستأجر والمالك |
| `POST /accounts/{id}/login` | دخول صامت للساس، يعيد مقبض جلسة | يفكّ التشفير داخلياً فقط |
| `GET /dashboard` · `GET /subscribers` · `POST /renewal/bulk` · `GET /report` (البلنك) · تذاكر | تمرير مُعزَّز إلى خدمة Python | حصر النطاق قبل التمرير |

**آلية التمرير:** الـ Controller يتحقق من التوكن + الصلاحية + المستأجر، يجلب `SasAccount` (مطابقاً `CompanyId` و`OwnerUserId` كدفاع بالعمق فوق فلتر المستأجر)، يفكّ تشفير الاعتماد، ثم ينادي خدمة Python الداخلية عبر HTTP على 127.0.0.1 مع رأس `X-Internal-Secret`، ويعيد البيانات المفلترة. **الاعتماد لا يغادر الخادم ولا يظهر في أي استجابة.**

## 3) المرحلة 3 — خدمة الساس Python (sidecar داخلي)

| # | المهمة | التفصيل |
|---|---|---|
| 3.1 | اشتقاق خدمة نحيلة من تطبيق الوكلاء | `sas_client.py` + `sas_user_client.py` + منطق `sas_panel`/`portal_sas`/`sas_sync` |
| 3.2 | تجريدها من مصادقة المستخدم النهائي | تثق فقط بـ localhost + `X-Internal-Secret` من .NET |
| 3.3 | جعلها بلا حالة (stateless) لكل طلب | تستقبل (ServerUrl + Username + Password) من .NET، أو معرّف حساب يخصّه .NET |
| 3.4 | ربطها على 127.0.0.1:8100 فقط | لا مسار Nginx عام لها إطلاقاً |
| 3.5 | (إن لزمت المزامنة) مخطط منفصل | Postgres schema `sas` أو SQLite، حلقة مزامنة لكل `SasAccount` |
| 3.6 | خدمة systemd `sas-service` | تشغيل تلقائي بجانب `sadara-api` |

**العزل:** الخدمة لا تعرف عن الشركات شيئاً — تنفّذ ما يطلبه .NET فقط باعتماد يمرّره .NET، وهي غير قابلة للوصول من الخارج.

## 4) المرحلة 4 — المصادقة: الدخول الصامت للساس (توسعة DualAuth)

| # | المهمة | الملف |
|---|---|---|
| 4.1 | إضافة `sasAccounts: [{id,label,type}]` (بلا أسرار) لاستجابة الدخول | `UnifiedAuthController.cs` |

**المنطق:** الموظف يدخل الصدارة مرة واحدة؛ إن كان له حساب ساس + صلاحية، يُهيَّأ جلسة الساس في الخلفية عبر `/api/sas-agent/accounts/{id}/login` فيفتح التبويب فوراً.

## 6) المرحلة 6 — تشديد العزل ومنع التسريب (قائمة تحقق شاملة)

| الخطر | الإجراء | حالة |
|---|---|---|
| تسرّب بين الشركات | كل كيان ساس `ITenantScoped` + فلتر مستأجر مُسجَّل | ☐ |
| كشف كلمة مرور الساس | تشفير Data Protection + DTO لا يحوي كلمة المرور | ☐ |
| وصول موظف بلا صلاحية | `[RequirePermission("sas_agent")]` على كل نقطة | ☐ |
| انتحال حساب موظف آخر | مطابقة `OwnerUserId == المستخدم` فوق فلتر المستأجر | ☐ |
| كشف خدمة Python | ربط 127.0.0.1 + `X-Internal-Secret` + بلا Nginx عام | ☐ |
| تجاوز العزل عبر `X-Api-Key` | منع مفتاح التكامل الداخلي من نقاط `sas-agent` | ☐ |
| تسرّب عبر السجلات | عدم تسجيل الاعتماد/التوكن؛ تدقيق وصول الساس فقط | ☐ |
| اختلاط ببيانات FTTH | مفتاح/اعتماد/وحدة/منبع منفصل تماماً عن FTTH | ☐ |
