# إصلاح جذري لثغرة RequirePermission fail-open — 2026-11-22

> تحليل + تطوير + اختبار في بيئة معزولة. **لم يُدمَج، لم يُنشَر، ولم تُعدَّل أي بيانات/صلاحيات إنتاج.** حساب «مزامنة» لم يُمَسّ.

## 1) السبب الجذري
`RequirePermissionAttribute.HasPermission` يُرجع `!failClosed` عند فراغ/غياب صلاحيات V2، والـattribute يُعامِل ذلك **fail-open افتراضياً** (`effectiveFailClosed = _failClosed || Authz:FailClosed`، والعلَم OFF). ⇒ أي مستخدم/حساب بعمود `FirstSystemPermissionsV2`/`SecondSystemPermissionsV2` فارغ **يُمنَح كل صلاحيات الميزات تلقائياً** (لأن `HasPermission` يُرجع true لأي مفتاح/إجراء عند الفراغ). تجاوز SuperAdmin ومنح CompanyAdmin لـ`linked_accounts` منفصلان (سليمان).

## 2) الحسابات المتأثرة (جرد كامل للإنتاج)
- **58 مستخدماً نشطاً**؛ **1 superadmin**.
- **حساب واحد بـV2 فارغ تماماً:** `مزامنة` (FullName «مزامنة»، Role=Employee=10، نشط، أُنشئ 2026‑05‑13، `LastLoginAt`=NULL). بصمته: أنشأ **12 قيداً محاسبياً + 12 سجل اشتراك + 1 معاملة فني** ⇒ حساب أتمتة/مزامنة منخفض الحجم يُجري **كتابة مالية**. عبر fail-open كان يملك وصولاً مالياً كاملاً.
- **صلاحيات الكتابة المحاسبية:** 12 مستخدماً يملكون `accounting.view`، **10 منهم** يملكون `add/edit/delete` (كتّاب شرعيون). ⇒ **مستخدمان «عرض‑فقط»** كان بإمكانهما الكتابة لأن نقاط الكتابة كانت تفحص `accounting.view` فقط.

## 3) نقاط API المكشوفة
- **أي نقطة محميّة بـ`[RequirePermission]` وحدها** تُفتَح لحساب بـV2 فارغ («مزامنة»). (النقاط الحسّاسة `sas_agent`/`property_registry`/`linked_accounts`/`ftth_operators` كانت أصلاً `failClosed:true` فمحميّة؛ والإدارية `DatabaseAdmin`/`SuperAdmin` بسياسة دور فمحميّة.)
- **17 نقطة كتابة مالية في `AccountingController`** كانت تعتمد على `accounting.view` الصنفي فقط (بلا صلاحية كتابة): `journal-entries` إنشاء/ترحيل/إبطال/تعديل/حذف، `cashboxes` إنشاء/إيداع/سحب/تعديل/حذف، `collections` إنشاء/تسليم/تعديل/حذف، `expenses` إنشاء/تعديل/حذف.

## 4) التغييرات البرمجية (فرع `security/require-permission-fail-closed`، commit `cd81e1e`)
- **`RequirePermissionAttribute.cs`:** fail-closed افتراضياً (secure-by-default). فراغ V2 ⇒ رفض. صمّام تراجع طارئ وحيد: `Authz:FailOpen=true` يعيد السلوك القديم فوراً (بلا إعادة نشر). تجاوز SuperAdmin ومنح CompanyAdmin محفوظان.
- **`AccountingController.cs`:** أُضيفت `[RequirePermission("accounting","add"/"edit"/"delete")]` على 17 نقطة كتابة ⇒ مستخدم العرض‑فقط لا يكتب/يعدّل/يحذف/يُرحّل.
- **`ServiceRequestsController.cs`:** بوّابتا التحصيلات (`accounting.collections/view`) والمهام (`tasks/add|edit`) المباشرتان صارتا `failClosed:true` اتساقاً.

## 5) نتائج الاختبارات
- **`AuthzFailClosedTests` (5، PostgreSQL فعلي):** فراغ V2 ⇒ 403؛ عرض‑فقط يرى ولا يكتب (403 على add/edit/delete)؛ كاتب بـadd يكتب؛ SuperAdmin مسموح رغم فراغ V2؛ صمّام `Authz:FailOpen` يعيد السماح.
- **التكامل الكامل (fix + security + A1 + C1 + C2): 314 ناجح / 0 فاشل**، بناء الحل ناجح، بلا تعارضات، بلا انحدار. (شمل إصلاح الأربعة القديمة + e2e دورة مالية.)

## 6) خطة معالجة «مزامنة» (أقل صلاحية — للعرض والموافقة، لم تُطبَّق)
| الحالي | المقترح (أقل امتياز) | الأثر |
|---|---|---|
| V2 فارغ (كل الصلاحيات عبر fail-open) | ختم V2 صريح بما يطابق بصمته فقط: `accounting:{view,add}` (لقيود التفعيل) + صلاحية إنشاء سجل اشتراك | يفقد الوصول غير المصرّح، ويحتفظ بوظيفة المزامنة فقط |
| — | **بديل إن ثبت أنه غير مستخدم** (LastLoginAt=NULL، آخر نشاط 2026‑10‑21): تعطيله | يُزيل سطح الخطر كلياً |
> **لا يُطبَّق دون موافقتك المستقلة (الشرط #8)** + تأكيد الخدمات/المهام المجدولة التي قد تستخدمه. **تحذير نشر: رفع الإصلاح دون ختم «مزامنة» أولاً سيوقف مزامنته** (fail-closed يرفضه).

## 7) خطة النشر والتراجع
**تسلسل مقترح:** `fix/preexisting-test-failures` → `security/...` → A1 → C1 → C2 (كلها كود فقط، بلا هجرات).
**ما قبل النشر:** (1) حسم «مزامنة» (ختم أقل صلاحية أو تعطيل) بموافقتك؛ (2) إعادة فحص الحسابات فارغة V2 لحظة النشر؛ (3) نسخة احتياطية + تحقّق استعادة.
**التراجع:**
- **فوري بلا نشر:** `Authz:FailOpen=true` في `appsettings.Production.json` (reloadOnChange) ⇒ يعيد fail-open خلال ثوانٍ إن ظهر حجب غير متوقّع.
- **كامل:** استعادة DLLs `dll_<TS>` + إعادة تشغيل.
**مؤشّرات النجاح/الفشل:** نجاح = مستخدمون شرعيون يعملون + «مزامنة» (بعد ختمها) تعمل + صفر 403 غير متوقّع في السجل + health 200. فشل = موجة 403 لمستخدمين شرعيين أو توقف مزامنة ⇒ رفع `Authz:FailOpen` فوراً + تحقيق.
**تحقّق بعد النشر:** راقب `journalctl` لـ403 المفاجئة دقائق + جرّب عملية محاسبية بمستخدم كاتب شرعي + `integrity-check`.

## الخلاصة
الثغرة أُغلقت **جذرياً** (secure-by-default) لا على حساب واحد، مع حماية كتابة مستقلة للعمليات المالية، وصمّام تراجع آمن، واختبارات تُثبت المنع. **بانتظار:** موافقتك على خطة «مزامنة» ثم الدمج/النشر التدريجي وفق الشرطين السابقين.
