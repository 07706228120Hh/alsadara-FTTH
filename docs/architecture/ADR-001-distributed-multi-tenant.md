- **الحالة (Status)**: مقترَح (Proposed) — بانتظار موافقة `project-manager` + المستخدم قبل بدء أي تنفيذ.
- **التاريخ**: 2026-08-02
- **المؤلّف**: architecture-evolution-agent (حارس البنية المعمارية).
- **المُراجِعون المطلوبون قبل التنفيذ**: `project-manager`، `security-auditor-agent` (نموذج الثقة/المفاتيح/العزل)، `database-postgres-agent` (تقسيم القاعدة/الترحيل)، `testing-qa-agent` (اختبار كل مرحلة)، `devops-agent` + `release-manager-agent` (توزيع العقد والتحديثات)، `integration-agent` (النفق + FTTH).
- **يبني على**: `docs/DB_MIRROR_SETUP.md`، عمل عزل المستأجرين الجاري على `feature/phase1-security` (الفلتر المركزي `ICurrentTenant`/`CurrentTenant`)، ADR ذاكرة القرارات `.claude/memory/DECISIONS.md`.

> **تنويه القواعد الذهبية**: هذه الوثيقة تصميم فقط. لم يُعدَّل أي كود تطبيقي أو schema. أي تنفيذ لاحق يمرّ عبر `project-manager` ثم الوكلاء المختصين مع موافقة بشرية صريحة على: تغيير المصادقة (RS256)، تغيير عزل المستأجرين، تغيير البنية التحتية، وأي migration إنتاج.

## 1. السياق والوضع الحالي (Context)

### 1.1 الوضع الحالي — قاعدة مركزية واحدة

اليوم منصة الصدارة تعمل بنموذج **multi-tenant مركزي مشترك (shared-database, shared-schema)**:

- **قاعدة واحدة** `sadara_db` على PostgreSQL 16 في VPS `72.61.183.61`، تحوي بيانات كل الشركات مختلطة في نفس الجداول.
- **العزل منطقي فقط** عبر عمود `CompanyId` + فلتر مركزي في `SadaraDbContext` يقرأ هوية الشركة من claim التوكن (`company_id`) عبر `ICurrentTenant`/`CurrentTenant`، مع تجاوز (bypass) لـ `SuperAdmin`/سياق النظام/مفتاح API الداخلي/الطلب غير المُصادَق.
- **API واحد** (`Sadara.API`, .NET 9، 57 controller) يخدم كل الشركات، منشور كـ systemd service `sadara-api`.
- **مصادقة متماثلة (HS256)**: `JwtService` يوقّع التوكن بمفتاح **سرّي مشترك** (`SymmetricSecurityKey` + `HmacSha256`)، صلاحية افتراضية 60 دقيقة. نفس السر يوقّع ويتحقّق — لا يصلح لنموذج موزّع (أي عقدة تملك السر تستطيع تزوير توكنات).

### 1.2 نقاط الألم التي تدفع للتحوّل

| # | المشكلة | الأثر |
|---|---------|-------|
| 1 | كل بيانات الشركات على سيرفر واحد | خصوصية: مالك السيرفر يرى بيانات الجميع؛ خرق واحد = تسرّب شامل. عزل منطقي فقط. |
| 2 | نقطة فشل واحدة (SPOF) | تعطّل VPS أو القاعدة = توقّف كل الشركات. |
| 3 | خطر خطأ العزل المنطقي | نسيان فلتر `CompanyId` في استعلام واحد = تسرّب بين الشركات (P0 مفتوح في التقييم الحالي). |
| 4 | التحجيم المشترك | حمل شركة كبيرة يؤثر على البقية (jitter، I/O). |
| 5 | متطلّب العميل | الشركات تريد بياناتها التشغيلية **داخل مكاتبها** (سيادة بيانات + عمل داخل الشبكة المحلية بسرعة). |

### 1.3 القرارات المؤكّدة من المستخدم (مدخلات ثابتة — لا تُعاد مناقشتها)

1. لكل شركة **"حاسبة رئيسية" في مكتبها** تعمل خادماً محلياً يشغّل (API .NET 9 + PostgreSQL محلي). بقية أجهزة/هواتف الشركة تتصل بها داخل الشبكة المحلية مباشرة، وعن بُعد عبر **نفق آمن** (Tailscale/Cloudflare Tunnel). **منفذ PostgreSQL 5432 لا يُعرَّض للإنترنت إطلاقاً — فقط الـ API عبر HTTPS.**
2. **backend لامركزي كامل**: كل شركة تشغّل نسخة API + قاعدة PostgreSQL محلية خاصة بها.
3. **المركز (`72.61.183.61`) = سلطة الهوية والترخيص فقط**: Super Admin، سجل الشركات وحالة الترخيص، حسابات مديري الشركات، الصلاحيات/الخدمات (نظام `ServiceAndPermission` الموجود). يُصدر JWT موقّعاً بمفتاح **خاص RS256**، وكل عقدة محلية تتحقّق بالمفتاح **العام** دون اتصال بالمركز في كل طلب. الدخول يتطلب اتصالاً بالمركز، والتوكن صالح **24 ساعة** (grace period).
4. **اتجاه البيانات**: المركز يمنح الهوية فقط — **لا بيانات تشغيلية تعود للمركز إطلاقاً** (عزل كامل وخصوصية تامة).
5. **الاستثناء**: شركة "الصدارة" الحالية تبقى بياناتها التشغيلية على المركز كما هي (الشركة المرجعية الوحيدة على السيرفر الرئيسي).

## 2. القرار المعماري المستهدف (Decision)

### 2.1 الجوهر

الانتقال من **قاعدة مركزية مشتركة** إلى نموذج **هجين موزّع (Hybrid Distributed Multi-Tenant)** بفصل واضح بين طبقتين:

- **طبقة الهوية والترخيص المركزية (Central Identity & Licensing Authority — CILA)** على `72.61.183.61`: تدير *من أنت* و*هل يُسمح لشركتك بالعمل* و*ما صلاحياتك*. مصدر الحقيقة الوحيد للهوية.
- **العقد التشغيلية المحلية (Local Operational Nodes — LON)** في مكاتب الشركات: كل عقدة تملك *بيانات شركتها التشغيلية بالكامل* في قاعدتها المحلية، وتتحقّق من التوكن ذاتياً بالمفتاح العام.

الفصل جوهرياً هو **فصل مستوى Bounded Context**: سياق الهوية/الترخيص (Identity) منفصل عن السياق التشغيلي (Operations). هذا يتماشى مع Clean Architecture الحالية — نُبقي نفس الطبقات (API → Application → Domain ← Infrastructure) في كلا الجانبين، لكن نقسّم **الكيانات** (DbSets) بين قاعدتين حسب السياق.

### 2.3 المبادئ المعمارية الحاكمة

1. **مصدر حقيقة واحد للهوية**: المركز فقط يصدر التوكنات. لا عقدة تصدر توكناً.
2. **تحقّق لامركزي بلا حالة (stateless)**: العقدة تتحقّق من التوقيع بالمفتاح العام محلياً؛ لا استدعاء للمركز في كل طلب (متانة ضد انقطاع الإنترنت خلال صلاحية التوكن).
3. **خصوصية بالتصميم (Privacy by design)**: البيانات التشغيلية لا تغادر العقدة أبداً. المركز لا يرى صفّاً تشغيلياً واحداً (عدا استثناء الصدارة §5).
4. **العزل يصبح فيزيائياً**: بدل عمود `CompanyId` كحاجز منطقي وحيد، تصبح كل شركة في قاعدة/خادم منفصل فيزيائياً. هذا يُبسّط نموذج العزل داخل العقدة (عقدة واحدة = شركة واحدة).
5. **إبقاء Clean Architecture**: نفس الطبقات في المركز وفي العقدة؛ التقسيم يقع على مستوى الكيانات/DbContext لا على مستوى نمط الطبقات.

## 3. نموذج الثقة (Trust Model) — JWT RS256

### 3.1 لماذا RS256 (غير متماثل) وليس HS256 (الحالي)

النموذج الحالي HS256 يستخدم سرّاً مشتركاً واحداً للتوقيع والتحقّق. في نموذج موزّع هذا **غير آمن**: كل عقدة محلية ستحتاج السر للتحقّق، وبذلك تستطيع كل عقدة (أو من يخترقها) **تزوير توكنات لأي شركة**. الحل: RS256 (زوج مفاتيح غير متماثل):

- **المفتاح الخاص (Private Key)**: يبقى **حصراً في المركز**، يوقّع التوكنات. لا يغادر `72.61.183.61` أبداً.
- **المفتاح العام (Public Key)**: يُوزَّع على كل العقد، يتحقّق فقط من التوقيع ولا يمكّن من التزوير.

### 3.2 دورة حياة التوكن

```
1. الموظف/المدير يفتح التطبيق → يُدخل بيانات الاعتماد.
2. الطلب يذهب للمركز (CILA) عبر HTTPS.
3. المركز يتحقّق: كلمة المرور صحيحة؟ + الشركة مفعّلة (IsActive + ليست منتهية/موقوفة)؟ + المستخدم نشط؟
4. المركز يُصدر JWT RS256 يحوي: sub, role, company_id, node_id, license_exp, jti, iat, exp(=iat+24h).
5. التطبيق يحفظ التوكن ويتصل بالعقدة المحلية (LAN أو نفق) حاملاً التوكن.
6. العقدة تتحقّق من التوقيع بالمفتاح العام محلياً (لا اتصال بالمركز) + تتحقّق exp + تتحقّق company_id == هوية العقدة.
7. صلاحية 24 ساعة: التطبيق يعمل حتى لو انقطع الإنترنت عن المركز خلال هذه المدة (grace period).
8. عند انتهاء الـ 24 ساعة → التطبيق يُعيد التوجيه لتسجيل دخول جديد (يتطلب اتصال المركز مجدداً).
```

**مطالبات (Claims) مقترحة للتوكن الموزّع** (توسعة للموجود في `JwtService`):

| Claim | الغرض | مصدره |
|-------|-------|-------|
| `sub` | معرّف المستخدم | موجود |
| `role` | الدور (`UserRole`) | موجود |
| `company_id` | هوية الشركة/العقدة — العقدة ترفض أي توكن لا يطابق هويتها | موجود |
| `node_id` | (جديد) معرّف العقدة المحلية المصرّح لها | سجل الشركات |
| `license_exp` | (جديد) تاريخ انتهاء ترخيص الشركة — العقدة تفشل-مغلقة بعده | سجل الترخيص |
| `perm_hash` أو snapshot الصلاحيات | (جديد) بصمة الصلاحيات لحظة الإصدار | نظام ServiceAndPermission |
| `jti`, `iat`, `exp` | معرّف التوكن + الإصدار + الانتهاء (24h) | موجود/معدّل |

### 3.3 آلية الإبطال / توقيف شركة (Revocation)

التحدّي الجوهري في التوكن اللامركزي: التوقيف الفوري صعب لأن العقدة لا تسأل المركز في كل طلب. الحل بطبقات:

1. **صلاحية قصيرة نسبياً (24h)**: الحد الأعلى للضرر بعد التوقيف = 24 ساعة (حتى انتهاء آخر توكن صادر). مقبول ضمن قرار المستخدم.
2. **بوابة الدخول عند المركز**: عند توقيف شركة (`Company.IsActive = false` / `SuspendedAt`) لن تُصدَر توكنات جديدة → بعد 24 ساعة تتوقّف العقدة كلياً عن قبول أي مستخدم.
3. **`license_exp` داخل التوكن**: العقدة نفسها تفشل-مغلقة إن تجاوزت الساعة الحالية `license_exp` (لا تحتاج المركز).
4. **فحص خفيف عند التوفّر (heartbeat اختياري)**: عند وجود اتصال، العقدة تستعلم دورياً (مثلاً كل ساعة) عن قائمة توقيف قصيرة (CRL/denylist بـ `jti` أو `company_id`) لتسريع الإبطال دون كسر العمل offline. **لا يُرسَل أي بيان تشغيلي** — فقط استعلام حالة.
5. **kill-switch للعقدة**: عند التوقيف الدائم، المركز يوقف تجديد المفتاح العام/الترخيص، والعقدة تُظهر شاشة "الترخيص موقوف — راجع الإدارة".

> القرار النهائي في تصميم الإبطال (هل نكتفي بالـ 24h أم نضيف CRL) بيد `security-auditor-agent`. التوصية المعمارية: 24h + `license_exp` كخط أساس، وCRL heartbeat كتحسين مرحلة لاحقة.

### 3.4 تخزين المفاتيح بأمان

- **المفتاح الخاص (المركز)**: يُخزَّن خارج المستودع — في متغيّر بيئة/secret store على `72.61.183.61` بصلاحيات `600` لمستخدم الخدمة فقط. **لا يُلتزم في git، لا يُطبع** (القاعدتان 6 و7). يُفضّل HSM/ملف مشفّر إن أمكن مستقبلاً. تدوير المفتاح عبر معرّف `kid` في رأس التوكن + نشر مفاتيح متعددة عبر JWKS.
- **المفتاح العام (العقدة)**: يُوزَّع مع مُثبِّت العقدة و/أو يُجلب من نقطة `/.well-known/jwks.json` على المركز عند الإقلاع ودورياً. المفتاح العام غير سرّي، لكن يجب حماية **سلامته** (integrity): يُجلب حصراً عبر HTTPS (TLS pinning للمركز مستحسن) كي لا يُستبدل بمفتاح مهاجم عبر MITM. تُخزّن نسخة محلية موقّعة/مثبّتة للعمل offline.
- **الأثر على الكود الحالي**: `JwtService` (يستخدم `SymmetricSecurityKey`/`HmacSha256`) يجب أن يتحوّل لـ `RsaSecurityKey`/`RS256` في المركز، وإعداد `AddJwtBearer` في كل عقدة يستخدم `RsaSecurityKey` (المفتاح العام) بدل السر. **هذا تغيير مصادقة → يمرّ إلزامياً على `security-auditor-agent` (القاعدة 14).**

## 4. تصنيف الجداول: هوية/ترخيص (تبقى في المركز) مقابل تشغيلية (تنتقل للعقدة)

### 4.1 قاعدة التصنيف

- **(أ) هوية/ترخيص/صلاحيات → المركز (`sadara_identity_db`)**: كل ما يجيب "من أنت؟"، "هل يُسمح لشركتك؟"، "ما صلاحياتك؟". بيانات مرجعية/تعريفية عابرة للشركات أو ضرورية للمصادقة قبل الوصول للعقدة.
- **(ب) تشغيلية → العقدة المحلية لكل شركة (`sadara_node_db`)**: كل ما ينتجه العمل اليومي للشركة (مشتركون، محاسبة، مهام، مخزون، محادثات...). هذه لا تعود للمركز أبداً (§4 من قرارات المستخدم).

المرجع: `SadaraDbContext` (كل الـ DbSets) + كيانات `Sadara.Domain`.

### 4.2 جدول التصنيف

| المجموعة | كيانات/جداول (DbSets) | التصنيف | ملاحظة |
|----------|------------------------|---------|--------|
| **الهوية والمستخدمون** | `Users` | **(أ) مركز** (مع نسخة تشغيلية — انظر الحالة الغامضة #1) | المصادقة مركزية؛ لكن الموظف مرتبط ببيانات تشغيلية على العقدة |
| **الشركات والترخيص** | `Companies`, `CompanyServices`, `CompanyFtthSettings` | **(أ) مركز** | سجل الشركات + حالة الترخيص + الخدمات المفعّلة |

### 4.3 الحالات الغامضة (كيانات على الحدود) والمعالجة المقترحة

1. **`Users` (الأصعب)**: المستخدم كيان *هوية* (مركز يصادق) وكيان *تشغيلي* (مرتبط بـ FK من عشرات الجداول التشغيلية على العقدة: `AssignedToId`, `TechnicianId`, `GrantedById`...).
   - **المقترح (نمط "الهوية المركزية + الملف التشغيلي المحلي")**: المركز يملك **سجل الهوية المصدري** (بيانات الاعتماد، الدور، `CompanyId`، حالة النشاط، بيانات الأمان والجلسة). العقدة تحتفظ بـ **مرآة للقراءة (read replica) خفيفة** من مستخدمي شركتها (Id + الاسم + الدور + الصلاحيات لحظة الإصدار) تُحدَّث عند الدخول (من claims التوكن) — تكفي لإرضاء الـ FKs المحلية ولعرض "من نفّذ ماذا" دون أن تكون العقدة سلطة مصادقة. بيانات HR والراتب والحساب المالي للفني في `User` (تشغيلية بطبيعتها) تُنقل/تُدار على العقدة. **يحتاج قراراً مشتركاً بين `security-auditor` و`database-postgres` و`backend`.**
2. **`Companies`**: تعريف الشركة + الترخيص = مركز. لكن بعض حقول `Company` تشغيلية (شعار، إعدادات ميزات محلية). المقترح: يبقى `Company` في المركز كسجل ترخيص، وتُقرأ الإعدادات المحلية عبر التوكن/إعداد العقدة عند التزويد؛ ما هو تشغيلي بحت (تخصيصات محلية) يُدار محلياً.
3. **نظام المواطن + التجارة الإلكترونية (`Citizen*`, `Store*`, `Order*`, `Product*`, `Customer`, `Merchant`...)**: بطبيعته **مركزي/شركة-واحدة** — `Company.IsLinkedToCitizenPortal` يفرض "شركة واحدة فقط مرتبطة". هذا يطابق تماماً **استثناء الصدارة (§5)**: يبقى في المركز/عقدة الصدارة. لا يُوزَّع على كل العقد. القرار: يبقى مركزياً حتى/إلا إذا قرّر المنتج توزيعه.
4. **`UserFcmToken`**: رمز إشعار الجهاز. تشغيلي (يخص جلسة المستخدم على أجهزته)، لكن إرسال FCM قد يحتاج مساراً مركزياً. المقترح: يبقى على العقدة (إشعارات الشركة محلية)؛ إن احتاج المركز إرسال إشعار ترخيص، يمر عبر مسار منفصل. يقرّره `integration-agent`.
5. **`AppVersions`, `Settings`**: مرجعية للتحديثات. تُمركَز في المركز (لتوحيد التحديثات) وتُقرأ من العقد؛ أو تُكرَّر للقراءة. يقرّره `release-manager` + `devops`.
6. **بيانات FTTH cache (`FtthSubscriberCache`, `FtthSyncLog`)**: تشغيلية (عقدة). لكن مصدرها `api.ftth.iq` خلف Cloudflare (نقطة هشاشة). قرار: هل كل عقدة تزامن مباشرة مع FTTH أم يزامن المركز ويوزّع؟ **معماري + integration**: التوصية أن تزامن كل عقدة بيانات شركتها مباشرة (لا مرور بيانات عبر المركز، يحفظ §4)، مع إبقاء الجسر/whitelist IP.

### 4.4 استثناء "الصدارة" (§5)

عقدة "الصدارة" **ليست منفصلة** — بياناتها التشغيلية تبقى على `sadara_identity_db`/المركز كما هي اليوم. عملياً: المركز يستضيف (CILA) + (LON للصدارة) على نفس الخادم، بقاعدتين منطقيتين أو schema منفصلة. هذا يمنحنا **عقدة مرجعية حيّة على السيرفر نفسه** للاختبار قبل توزيع أي عقدة عميل — قيمة كبيرة للانتقال التدريجي (Strangler Fig).

## 5. الشبكة (Networking)

| البند | التصميم |
|-------|---------|
| **الوصول المحلي (LAN)** | أجهزة/هواتف الشركة داخل المكتب تتصل بالعقدة عبر IP محلي/mDNS، HTTPS بشهادة محلية (mkcert/CA داخلية) — سريع بلا إنترنت. |
| **الوصول عن بُعد** | نفق آمن: **Tailscale** (WireGuard mesh، أبسط للأجهزة) أو **Cloudflare Tunnel** (لا منفذ وارد مفتوح، مناسب لعناوين ديناميكية). يقرّره `devops`/`integration`. |

## 6. النسخ الاحتياطي المحلي لكل عقدة (Backup)

بعد التحوّل، **بيانات الشركة لم تعد على هوستنكر** — النسخ الاحتياطي المحلي يصبح **حرجاً (P0 تشغيلي)**؛ فقدان قرص حاسبة المكتب = فقدان كل بيانات الشركة.

- **إعادة استخدام البنية الموجودة**: `scripts/db_mirror_sync.ps1` (المبني وفق `docs/DB_MIRROR_SETUP.md`) يعتمد **pg_dump مجمّد كل 6 ساعات** كشبكة أمان حقيقية ضد الحذف/التلف. نُكيّفه ليعمل **محلياً على كل عقدة** ضد PostgreSQL المحلي بدل السحب عبر SSH.
- **قاعدة 3-2-1**: 3 نسخ، على وسيطين مختلفين، 1 خارج الموقع. المقترح لكل عقدة:
  1. نسخ محلية مجمّدة (على قرص/مجلد منفصل داخل الحاسبة).
  2. نسخة على قرص خارجي/NAS في المكتب.
  3. نسخة مشفّرة خارج الموقع — **مهم**: لحفظ §4 (لا بيانات للمركز)، تكون خارج الموقع **مخزناً تختاره الشركة أو تخزيناً مشفّراً client-side** بحيث لا يقرأ المركز/طرف ثالث المحتوى (تشفير قبل الرفع). يقرّره `security-auditor` + `database-postgres`.
- **مراقبة الفشل**: العقدة ترسل للمركز **إشارة صحّة نسخ احتياطي فقط** (نجح/فشل + طابع زمني، **بلا أي بيانات**) كي ينبّه Super Admin إن توقفت نسخ شركة. اختياري وبموافقة.
- **اختبار الاستعادة**: كل عقدة تُختبر استعادتها دورياً (نسخة لا تُختبَر ليست نسخة). `testing-qa` يضع الإجراء.

## 7. التحديثات (Updates & Deployment)

التحدّي: بدل خادم واحد نحدّثه بـ SCP، أصبح لدينا **N عقدة موزّعة** تحتاج تحديث API المحلي + التطبيق.

- **تطبيق العميل (Flutter alsadara-ftth)**: البنية موجودة — Inno Setup → GitHub Releases → auto-update عبر `auto_update_service`. هذه تغطي أجهزة الموظفين بالفعل. تُبقى كما هي.
- **API العقدة (.NET 9) — الجديد**: يحتاج آلية تحديث للحاسبة الرئيسية لكل شركة. خيارات:
  1. **حزمة تحديث موقّعة** ينشرها المركز؛ خدمة محدّث على العقدة (Windows service) تسحب النسخة الجديدة، تتحقّق من التوقيع، تطبّق migrations محلياً، تعيد تشغيل الخدمة — بنمط auto-update مشابه للتطبيق.
  2. **حاوية (Docker)**: العقدة تشغّل API في حاوية؛ التحديث = سحب image موقّع. (`docker/Dockerfile` موجود). أنظف لإدارة الإصدارات لكن يتطلب Docker على حاسبة المكتب.
- **تطابق الإصدارات (schema/API)**: خطر رئيسي (§8). كل تحديث API يحمل رقم إصدار schema؛ **migrations idempotent** تُطبَّق تلقائياً عند الإقلاع مع نسخة احتياطية pre-migration إلزامية. المركز يتتبّع إصدار كل عقدة عبر heartbeat الإصدار (رقم فقط) وينبّه للعقد المتخلّفة. توافق التوكن للأمام/للخلف عبر claims مرن.
- **الموافقات**: توزيع أي تحديث عقد = عملية إنتاج واسعة الأثر → موافقة صريحة + `release-manager` + `devops` + `testing-qa`.

## 8. تدفّق Onboarding لشركة جديدة

```
1. Super Admin في المركز → ينشئ Company (Name, Code, الترخيص، الخدمات، الميزات) + حساب CompanyAdmin.
   (يعيد استخدام CompaniesController + نظام ServiceAndPermission الموجود)
2. المركز يولّد node_id + إعداد عقدة موقّع (يحوي: عنوان المركز/JWKS، company_id، node_id،
   المفتاح العام، إعداد النفق) — بلا أي مفتاح خاص.
3. المركز يبني/يوفّر "حزمة عقدة جاهزة" = مُثبِّت (Inno Setup على نمط التطبيق) يحوي:
   API .NET 9 + PostgreSQL محلي + سكربتات النسخ الاحتياطي + المحدّث + الإعداد الموقّع.
4. تُنصّب الحزمة على حاسبة مكتب الشركة → تُنشئ القاعدة المحلية بـ schema فارغ + seed أساسي.
5. العقدة تنضم للنفق (Tailscale/CF) وتجلب المفتاح العام من JWKS، وتصبح جاهزة.
6. موظفو الشركة يسجّلون الدخول (المركز يصادق ويصدر توكن RS256) ويتصلون بالعقدة.
```

هذا يحوّل onboarding من عملية يدوية إلى **مُخرَج آلي من المركز** — يعيد استخدام سلسلة Inno Setup الموجودة، ويحفظ §4 (لا بيانات، فقط إعداد + مفتاح عام).

## 10. خطة الانتقال المرحلية (Migration Plan — Phases 0→6)

> كل مرحلة تمرّ عبر `project-manager` للتوزيع، وتُراجَع أمنياً (`security-auditor`) وقاعدياً (`database-postgres`) وتُختبَر (`testing-qa`) قبل الاعتماد. لا انتقال للمرحلة التالية قبل توثيق نتائج السابقة في `.claude/memory/DECISIONS.md`.

### المرحلة 0 — التأسيس والإثبات (Foundation & PoC)
- اعتماد هذا الADR (`project-manager` + المستخدم).
- **إتمام عمل عزل المستأجرين الجاري** (`feature/phase1-security`) وتفعيله بأمان — هو الأساس المنطقي قبل الفصل الفيزيائي (يضمن أن كل استعلام يحترم `CompanyId`، فيسهل الفصل لاحقاً). معالجة الـ 3×P0 المذكورة في PROJECT_STATE (config الإنتاج + backfill + تدوير `InternalApiKey`).
- إثبات مفهوم RS256: توليد زوج مفاتيح + PoC توقيع مركزي/تحقّق محلي في بيئة محلية (بلا مساس إنتاج). مالك: `security-auditor` + `backend`.

### المرحلة 1 — سلطة الهوية المركزية (CILA) وRS256
- إنشاء حدود سياق الهوية: تحديد/عزل الكيانات (أ) في وحدة/DbContext هوية.
- تحويل `JwtService` لـ RS256 (توقيع مركزي) + `AddJwtBearer` للتحقّق بالمفتاح العام، مع **تشغيل مزدوج** (HS256+RS256) للانتقال. نشر JWKS. **موافقة `security-auditor` + المستخدم (تغيير مصادقة).**
- إضافة claims `node_id`/`license_exp` وتمديد الصلاحية لـ 24h خلف إعداد.

### المرحلة 2 — تقسيم القاعدة منطقياً (Logical Split)
- فصل القاعدة إلى schema/DbContext هوية مقابل تشغيلي وفق §4، **دون** توزيع فيزيائي بعد (كلاهما ما زال على المركز). مالك: `database-postgres` + `backend` + `architecture`.
- حسم الحالات الغامضة §4.3 (خصوصاً `Users` — نمط الهوية المركزية + الملف التشغيلي).
- migrations بخطة rollback + نسخ احتياطية (القاعدة 10). اختبار `testing-qa` مكثّف لعزل الاستعلامات.

### المرحلة 3 — تجهيز حزمة العقدة (Node Package)
- بناء مُثبِّت عقدة (API + PostgreSQL محلي + سكربتات نسخ احتياطي مكيّفة من `db_mirror_sync.ps1` + محدّث) عبر Inno Setup/Docker. مالك: `devops` + `release-manager` + `database-postgres`.
- أتمتة توليد الإعداد الموقّع + توزيع المفتاح العام (§8). إعداد النفق (`integration`/`devops`).

### المرحلة 4 — العقدة التجريبية (Pilot Node)
- نشر عقدة واحدة لشركة تجريبية متطوّعة (أو عقدة داخلية). ترحيل بياناتها من المركز للعقدة (export مُقيَّد بـ `CompanyId` → import محلي). تشغيل مزدوج/موازٍ للتحقّق. مالك: كل الفريق بإشراف `testing-qa`.
- تفعيل النسخ الاحتياطي المحلي + اختبار استعادة + heartbeat مراقبة.

### المرحلة 5 — التوزيع التدريجي (Rollout — Strangler Fig)
- ترحيل الشركات عقدة تلو الأخرى، لكل واحدة: export مُقيَّد → import محلي → تحقّق → قطع من المركز. **موافقة صريحة لكل شركة** (بياناتها تنتقل). أتمتة onboarding للجديدات (§8).
- تعطيل تدريجي للمسارات المركزية للبيانات التشغيلية المُرحَّلة.

### المرحلة 6 — تثبيت المركز على دور الهوية + استثناء الصدارة
- المركز يحتفظ فقط بـ (أ) + بيانات الصدارة التشغيلية (§5) كعقدة مرجعية على نفس الخادم.
- إزالة الكود التشغيلي المشترك القديم من المركز (بعد التأكد أنه لم يعد يخدم غير الصدارة). توثيق نهائي + تحديث `ARCHITECTURE.md`.

## 11. تأثير التحوّل على القواعد الذهبية والأمان والعزل

- **العزل (Isolation)**: يترقّى من **منطقي (عمود `CompanyId`)** إلى **فيزيائي (قاعدة/خادم منفصل)** — أقوى ضمانة خصوصية. لكن عمل العزل المنطقي الحالي **لا يُهمَل**: يبقى ضرورياً داخل المركز (يخدم عدة شركات في طبقة الهوية) وأثناء الانتقال (المرحلة 2 قبل الفصل الفيزيائي). القاعدة 14 (أي تغيير عزل يمرّ على `security-auditor`) تنطبق على كل مرحلة.
- **المصادقة (القاعدة 14)**: التحوّل لـ RS256 وتمديد الصلاحية لـ24h هو **تغيير نظام المصادقة** — يتطلب موافقة صريحة ومراجعة `security-auditor` قبل أي تنفيذ.
- **قاعدة البيانات (القاعدة 15)**: تقسيم القاعدة والترحيل يتطلب `database-postgres-agent` + خطط rollback (القاعدة 10) + نسخ احتياطية.
- **البنية التحتية (Human Approval)**: توزيع عقد محلية + أنفاق + محدّثات = تغيير بنية تحتية جوهري → موافقة بشرية.
- **الأسرار (القاعدتان 6/7)**: المفتاح الخاص لا يُلتزم ولا يُطبع؛ يعامل كأعلى سر في المنصة.
- **الأثر على Clean Architecture**: النمط يبقى سليماً (الطبقات كما هي). ما يتغيّر هو تقسيم الكيانات على سياقين وقاعدتين — نضيف حدود Bounded Context دون كسر اتجاه التبعيات.

## 12. البدائل المدروسة (Alternatives Considered)

| البديل | لماذا لم يُختَر |
|--------|----------------|
| **البقاء مركزياً مع تقوية RLS/العزل المنطقي** | لا يحقّق متطلّب المستخدم (بيانات داخل مكاتب الشركات) ولا السيادة/الخصوصية الفيزيائية؛ يبقي SPOF. |
| **قاعدة لكل مستأجر على نفس الخادم المركزي (DB-per-tenant مركزي)** | يحسّن العزل لكن يبقي البيانات على هوستنكر (يخالف §4/§5) ويبقي SPOF. |
| **توكن قصير الأجل + استدعاء المركز في كل طلب** | يكسر العمل offline ويجعل المركز SPOF لكل طلب؛ يخالف قرار الـ24h grace. |
| **مزامنة ثنائية الاتجاه عقدة↔مركز** | يخالف §4 صراحةً (لا بيانات تشغيلية للمركز) ويضاعف التعقيد وسطح الهجوم. |
| **النموذج الهجين المختار (RS256 + عقد لامركزية + هوية مركزية)** | **المُعتمد**: يحقّق السيادة والخصوصية والعمل offline مع سلطة هوية واحدة، ويعيد استخدام أصول موجودة (Inno Setup، نظام الصلاحيات، سكربتات النسخ). |

## 13. القرار (Decision Record)

نعتمد **النموذج الهجين الموزّع**: مركز CILA لسلطة الهوية/الترخيص/الصلاحيات يصدر JWT RS256 صالح 24h، وعقد تشغيلية محلية لامركزية لكل شركة (API + PostgreSQL محلي) تتحقّق ذاتياً بالمفتاح العام، بلا عودة أي بيانات تشغيلية للمركز، مع استثناء بقاء بيانات "الصدارة" على المركز. التنفيذ عبر 7 مراحل (0→6) مربوطة بعمل عزل المستأجرين الجاري، وكل مرحلة تمرّ عبر سلسلة الموافقات والمراجعات وفق القواعد الذهبية.

**الحالة تبقى "مقترَح" حتى موافقة `project-manager` والمستخدم على بدء المرحلة 0.**
