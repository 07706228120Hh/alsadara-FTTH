# خطة بنية «الشركاء الرئيسيون» لمحاسبة FTTH

**الحالة:** مُوثَّقة — بانتظار بدء التنفيذ المرحلي.
**التاريخ:** 2026-10-24. **القرار:** مالك موقّع (عدّة شركاء رئيسيين، موظفون عبرهم).

> مكتوبة لمن ينفّذ الميزة (وكلاء/جلسات لاحقة). كل مرحلة تمرّ ببوّابة موافقة + فحص قبل التالية.

---

## 1) المشكلة
- شركة الصدارة لها **عدّة شركاء FTTH رئيسيين** (كل شريك = حساب رئيسي بـ`AccountId` فريد، مثل 2261175/2834953/3171968).
- **الموظف الواحد** (مثل رسول) له حسابات **فرعية عند عدّة شركاء** (اسم مستخدم مختلف لكل شريك).
- القيود الحالية:
  1. التطبيق يجلب عمليات FTTH من **حساب واحد مُسجَّل الدخول** فقط ⇒ شريحة شريك واحد.
  2. المزامنة **تُتلف هوية المشغّل**: `SubscriptionLog.ActivatedBy` يُستبدَل بالاسم المحلول (`_resolveFullNameFromMap`) فيُفقَد `createdBy` الخام.
  3. حقلا `SubscriptionLog.PartnerId/PartnerName` موجودان لكن **لا يُملآن** (التطبيق لا يرسل `tx.partner`).
  4. لا عزل/تمييز بين شركاء يتشاركون أسماء مستخدمين متطابقة.

## 2) المبادئ الحاكمة
- **الشريك الرئيسي = مصدر الجلب الموثوق** (حسابه يرى كل فروعه عبر `walletOwnerType=partner`).
- **المطابقة على معرّفات ثابتة** لا أسماء معروضة: `PartnerId` → `OperatorUsername` (createdBy الخام) → اسم المواطن (حكم أخير).
- **مصدر حقيقة واحد**: الشريك يُختم على **العملية** (`SubscriptionLog`)؛ الفني يَرِث نسخة؛ القيد يُشتَقّ.
- العزل بالشركة (`CompanyId` من التوكن) يبقى فوق كل شيء.

## 3) الكيانات والتغييرات
| الكيان | التغيير | ملاحظة |
|------|------|------|
| `FtthPartner` (جديد) | `CompanyId, Name, MainUsername, MainPasswordEncrypted, PartnerAccountId?, ServerUrl, IsActive, Status, LastVerifiedAt` | الحساب الرئيسي = مصدر الجلب. الاعتماد مشفّر عبر `ISecretProtector`، لا يُعاد في أي استجابة. |
| `FtthAccount` | `+ PartnerId (FK→FtthPartner)` | كل حساب موظف يتبع شريكاً. كلمة مرور الفرعي **إلزامية** (قرار المالك). |
| `SubscriptionLog` | `+ OperatorUsername` (createdBy خام، لا يُستبدَل) + ملء `PartnerId/PartnerName` فعلياً من `tx.partner` | `ActivatedBy` يبقى للعرض فقط. |
| `TechnicianTransaction` | `+ PartnerId + OperatorUsername` (نسخة من العملية) | لتقارير/تسويات الفني لكل شريك (مؤكّد مطلوب). |
| `JournalEntry` | — (يُشتَقّ عبر العملية) | لا تكرار الآن؛ يُضاف لاحقاً فقط لو لزمت قوائم مالية لكل شريك. |

## 4) التدفّقات
- **شاشة الشركاء:** CRUD شريك = اسم + اعتماد رئيسي (يوزر+باسوورد) + «توثيق» (دخول خادمي يلتقط `PartnerAccountId` من JWT).
- **ربط حساب موظف (تبويب الحسابات المرتبطة · FTTH):** اختر الشريك → endpoint «مشغّلو الشريك» (دخول رئيسي خادمي → أسماء مستخدمين من `/api/teams/members`، بلا أسرار) → اختر الاسم من القائمة → اكتب كلمة المرور → توثيق → يُخزَّن `(OwnerUserId, PartnerId, Username, PasswordEncrypted)`.
- **تبويب الحسابات (المقارنة):** فلتر بالشريك + خيار «الكل» (مشترك).
- **محرّك المزامنة متعدّد الشركاء:** الخادم يجمّع الحسابات حسب الشريك، ولكل شريك يسجّل دخول حسابه الرئيسي، يجلب كل العمليات، **يوسم كل عملية بـ`PartnerId` و`OperatorUsername`**، يجمّع عبر الشركاء، ويحذف المكرّر بـ`FtthTransactionId`. يطبّق الاستبعاد الموجود.
- **المطابقة:** `(PartnerId + OperatorUsername)` → `FtthAccount(PartnerId, Username)` → `OwnerUserId`؛ رجوع: `OperatorUsername` وحده (مع صمام الغموض) ثم اسم المواطن.

## 5) الخطة المرحلية (بوّابة + فحص لكل مرحلة)

| م | العمل | البوّابة | الفحص قبل التالية |
|:-:|------|------|------|
| **1** | كيان `FtthPartner` + `FtthAccount.PartnerId` + `SubscriptionLog.OperatorUsername` + migration | موافقة + نسخة احتياطية قبل التطبيق | بناء 0 أخطاء؛ الهجرة CreateTable/AddColumn فقط (لا DROP)؛ تُطبَّق على staging/مرآة أولاً |
| **2** | CRUD الشركاء (باكند) + توثيق الرئيسي + endpoint «مشغّلو الشريك» | معزول بالشركة؛ اعتماد مشفّر لا يُعاد | اختبار: إضافة/توثيق شريك؛ جلب أسماء المشغّلين بلا تسريب سرّ |
| **3** | شاشة الشركاء (Flutter) + تعديل ربط الحساب (اختيار الشريك + قائمة الأسماء) | إصدار تطبيق (tag) | analyze نظيف؛ دخان تشغيلي؛ ربط حساب فعلي ينجح |
| **4** | المزامنة متعدّدة الشركاء: جلب لكل شريك + وسم `PartnerId/OperatorUsername` + حذف المكرّر + إيقاف إتلاف `createdBy` | يكتب بيانات؛ idempotent؛ موافقة | عدّ قبل/بعد؛ لا تكرار؛ العمليات تحمل الشريك والمعرّف الخام |
| **5** | المطابقة الثلاثية (شريك→مشغّل→مواطن) + `TechnicianTransaction.PartnerId/OperatorUsername` | يمسّ المحاسبة | رصيد الفني يبقى صحيحاً؛ النسبة للموظف صحيحة عبر الشركاء |
| **6** | واجهة المقارنة: فلتر شريك + «الكل» + عرض المبلغ المجمّع للموظف | إصدار تطبيق | مطابقة رسول (3 شركاء) تظهر مجمّعة صحيحة |
| **7** | ردم `PartnerId/OperatorUsername` للعمليات القديمة (تدريجي عبر إعادة المزامنة) | يكتب بيانات | عيّنة تُردَم صحيحاً؛ لا انحدار أرصدة |

## 6) المخاطر والقرارات المثبّتة
- **قرارات المالك:** عدّة شركاء ✓؛ كلمة مرور الفرعي إلزامية ✓؛ `PartnerId` على الفني ✓؛ فلتر شريك + «الكل» ✓.
- **تصادم أسماء المستخدمين بين الشركاء:** يُحلّ بمفتاح (شريك + اسم). بلا شريك مخزّن ⇒ صمام الغموض يتخطّى.
- **الوصول للعمليات عبر حساب فرعي:** يُفترض أن الحساب الرئيسي يرى كل الفروع (`walletOwnerType=partner`) — **يجب التحقّق عملياً في المرحلة 4** قبل الاعتماد.
- **الأسرار:** اعتماد الشركاء والفروع مشفّر، لا يُطبع ولا يُعاد؛ أي كشف يمرّ على security-auditor-agent.
- **الهجرات:** إضافية فقط (AddColumn/CreateTable)؛ لا حذف/تعديل هجرة قائمة.
- **التوفيق:** snapshot الحالي لا يحوي فهارس منع الترحيل المزدوج (مطبّقة بـpsql) — يجب توفيقه قبل أي هجرة قادمة (المرحلة 1).
