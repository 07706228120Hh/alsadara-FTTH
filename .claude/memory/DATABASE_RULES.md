# DATABASE_RULES — قواعد قاعدة البيانات (PostgreSQL)

قواعد إلزامية للتعامل مع قاعدة بيانات منصة الصدارة. المالك الأساسي: `database-postgres-agent`.

## البيئة
- **المحرّك**: PostgreSQL، db = `sadara_db`.
- **خادم الإنتاج**: VPS رئيسي `72.61.183.61` (الوحيد المعتمد للنشر/الكتابة).
- **ORM**: EF Core 9 + Npgsql.
- **Migrations**: 84 migration حالياً تحت `src/Backend/Core/Sadara.Infrastructure/Data/Migrations`.

## قواعد Migrations
- إنشاء migration جديدة محلياً فقط، مع مراجعة الـ Up/Down يدوياً قبل أي تطبيق.
- **ممنوع** تشغيل migration على الإنتاج دون موافقة صريحة من المستخدم.
- التطبيق على الإنتاج يتم عبر خطوة مقصودة (EF migrate أو SQL مراجَع)، مع نسخة احتياطية مسبقة.
- كل migration يجب أن تملك `Down` صالحة للـ rollback.

## Rollback
- قبل أي تغيير بنيوي على الإنتاج: snapshot/نسخة احتياطية للقاعدة.
- في حال الفشل: استخدم `Down` للـ migration أو استعادة النسخة الاحتياطية.

## Tenant isolation (CompanyId)
- كل جدول مستأجر يجب فلترته بـ `CompanyId` في كل استعلام قراءة/كتابة.
- لا يجوز ترك استعلام يعبر حدود المستأجر. هذه قاعدة أمنية أيضاً (راجع `SECURITY_RULES.md`).

## RLS (Row-Level Security)
- وجود RLS فعلياً على القاعدة **Unknown** — يجب التحقق.
- توصية: تفعيل RLS على جداول المستأجرين كطبقة دفاع ثانية فوق فلترة `CompanyId` في الكود.

## Indexes
- التحقق من فهارس على `CompanyId` وعلى مفاتيح البحث المتكررة (FtthSubscriberCache، Subscription، Order).
- مراجعة خطط التنفيذ للاستعلامات البطيئة قبل إضافة فهارس عشوائية.

## ممنوعات
- لا SQL خام مدمّر (`DROP`, `TRUNCATE`, `DELETE` بلا `WHERE`) على الإنتاج دون موافقة.
- لا كتابة على خادم FTTH الخارجي `185.239.19.3` (قراءة فقط).
- لا تخزين أسرار/مفاتيح داخل الجداول بنص صريح.
- لا تطبيق migration تلقائي عند الإقلاع على الإنتاج دون مراجعة.
